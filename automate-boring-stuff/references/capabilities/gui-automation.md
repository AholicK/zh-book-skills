## I — 方法论骨架 (Interpretation)

兜底场景：没有 API/模块可用，只能模拟人操作界面——程序直接控制键鼠，向当前获得焦点的窗口发虚拟点击与按键（作者类比：「对一个机械臂编程」）。

核心矛盾：程序「相当盲目」——只按坐标和按键执行、无屏幕反馈，界面一变（窗口移位、被对话框挡住）就照指令点错；速度又快过人反应。所以先装三道护栏：① 注销兜底；② `pyautogui.PAUSE` 设秒数，每次调用后留出夺回键鼠的时间窗口；③ FAILSAFE——鼠标甩到屏幕左上角即触发 FailSafeException 急停。

脚本写法「先测量、再编写、加校验」：mouseNow 量坐标或 `locateOnScreen()` 找图 → `center()` → `click()`；点击前 `pixelMatchesColor()` 校验。总规则：错误指令下快速崩溃。

## A1 — 书中的应用 (Past Application)

### 案例 1: 18.4 项目 mouseNow.py——先测坐标再写脚本
- **类型**: 书中项目（第18章）
- **问题**: 光看屏幕弄不清像素坐标，写脚本前需测量工具
- **方法论的使用**: try/except KeyboardInterrupt 包住 while 循环，循环内 `x, y = pyautogui.position()` 原地刷新坐标；18.7 扩展版加 `getpixel((x, y))` 显示 RGB
- **结论**: 填表项目第 1 步先用它弄清确切坐标
- **结果**: 实测输出 `Press Ctrl-C to quit.` / `X: 290 Y: 424`；扩展版 `X: 406 Y: 17 RGB: (161, 50, 50)`

### 案例 2: 18.11 项目 formFiller.py——自动填表程序
- **类型**: 书中项目（第18章）
- **问题**: 数据重复填进另一个应用的表单；「只好不动脑子地点击和输入几个小时」
- **方法论的使用**: 先量首字段与 Submit another response 坐标；for 遍历：click() → typewrite()（'\t' 跳字段）→ 下拉/单选走键盘键 → press('enter') → sleep(5) 等加载 → 下一份表单
- **结论**: 灵活但「相当盲目」，需护栏与等待兜底
- **结果**: 会插入每个人的信息（示例 4 人）；未提供输出截图

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这张卡?

1. 自动填网页表单或重复点击，但没有 API/模块可用
2. 操作没有可编程接口的桌面软件；量屏幕坐标或「找图点击」某按钮
3. 键鼠模拟脚本写了一半，想让它可控、能叫停、点错就停
4. 半自动流程里复现一串人工操作（填表、上传、批量提交）

### 语言信号

- 「帮我自动填这个表单」「让脚本点这个按钮」「有没有办法自动操作软件」
- 英文: "auto fill form", "click for me", "control desktop app", "pyautogui"

### 与相邻能力的区分（阶段 3 定稿）

- 与 `debugging-toolkit` 的区别: 「点错就停/快速崩溃」与早失败思想同源（composes-with）；脚本不按预期跑时的排查走那条卡
- 与 `web-scraping` 的区别: 能走接口/选择器（selenium 类受控路径）就走那条；本卡是最后手段（contrasts-with）

## E — 可执行步骤 (Execution)

1. **先判场景、先装护栏**
   - 完成标准: 确认只能靠点击/键鼠完成（能走 `web-scraping` 的不进本流程）；PAUSE（书例 `pyautogui.PAUSE = 1`）、FAILSAFE、自救路径（甩左上角/注销）三件齐备
   - 判停条件: 高风险且无法加校验 → 放弃
2. **先测量、后写码**
   - 完成标准: mouseNow 量出目标坐标，或走 `locateOnScreen()`（逐像素匹配）→ `center()` → `click()`
3. **复现一次完整人工流程**
   - 完成标准: click 首字段 → `typewrite()`（'\t' 跳字段）→ 下拉/单选用键盘键 → 提交（`press('enter')`）→ `time.sleep()` 等加载；循环加 print() 报进度
4. **加校验、保快速崩溃**
   - 完成标准: 关键点击前校验（`pixelMatchesColor()` / `locateOnScreen()`），不匹配即停；保留 FAILSAFE/PAUSE；坐标与等待时间标注需重测

**输入契约**: 必需 = ①目标界面与操作序列；②坐标或目标截图（缺则先测）；③如何叫停。
**输出契约**: 「能叫停、点错就停」的脚本 + 坐标/等待参数 + 安全机制清单；每步可回指 f59 / f60 / f61 / f62 / f67 / p71 / p72。

## B — 边界 (Boundary) ★

### 不要在以下情况使用这张卡

- 有 API、模块或受控路径可用——先走那些（网页优先 `web-scraping` 的 selenium 类方案）
- 界面/分辨率频繁变化、需长期稳定复用（坐标会失效）；高风险且无法加校验
- 无人值守的批量任务（无反馈，错误指令会执行到底）

### 作者在书中警告的失败模式

- 失控：「如果程序自己在移动鼠标，停止它可能很难，你不能点击IDLE 窗口来关闭它」；速度「可能太快，导致其他程序跟不上」（ce35）
- 盲目：「可能会点击到错误的东西，造成严重破坏」——对策：「在得到错误指令时快速崩溃」、能校验「它没有点击在正确的东西上」而自行停止（ce35）
- 重跑需重测：「可能需要更新鼠标点击的坐标，因为浏览器窗口可能已经改变了位置」（ce35）
- 危险征兆（ce35）：无屏幕校验（getpixel / pixelMatchesColor / locateOnScreen）；FAILSAFE=False 或 PAUSE=0；硬编码坐标；出错后继续跑

### 作者盲点与底本缺口

- 平台差异大（unit_note）：Windows 直接 pip install pyautogui；OS X/Linux 需先装依赖（pyobjc-core/pyobjc、python3-xlib + scrot + tk），未给现代系统核对；与 `debugging-toolkit`（v09）和 `web-scraping`（v10）构成对照（unit_note）
- 「被对话框挡住」恢复流程未给（V2 遗漏点）；多显示器/缩放坐标与逐像素匹配失败未涉（f60/f61）；组合键非英文布局差异未讲（f67）；Google 表单外链或失效（f62）
- 版本风险（nr_warnings）：本书示例为 2016 年版；现代同名库可能已改名或调整语义，执行前按当前官方文档核对——外推提示、非书内内容；据其产生的失败不计为能力缺陷

### 容易混淆的邻近方法论

- `debugging-toolkit`: 早失败与排障；`web-scraping`: 能走受控路径就不该用键鼠模拟
