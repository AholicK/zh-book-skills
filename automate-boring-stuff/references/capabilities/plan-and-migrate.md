## I — 方法论骨架 (Interpretation)

跨任务的开工与迁移元方法，四个环环相扣的习惯：

① 开工先计划：先「后退一步」列「程序要做的事」（自然语言，暂不想代码），再翻译成「代码要做的事」（对得上具体 API）；清单即路线图，逐条关注、每步独立可验证。

② 先笨后巧：不理解新工具的价值时，先写不用它的笨版本（样板：手写 isPhoneNumber 只支持一种模式）并跑通，再引入正则一类工具重写。

③ 危险动作先预演：会改动真实数据前，先注释危险部分、先 print 待处理清单确认。

④ 交付后迁移：完成后按「类似程序的想法」模板列 2–4 条新用途（动词短语起头；需别的章节能力时显式交叉引用），不改动原程序。

贯穿取舍（p04）：「写完就能跑」优先于风格（个人一次性脚本）；团队协作与长期维护不在适用面内。数独类比同理——编程 = 把问题分解为单个、详细的步骤。

## A1 — 书中的应用 (Past Application)

### 案例 1: 大学室友在电子产品零售店写程序比价（几小时 vs 3 人两天）
- **类型**: 书中转述（前言）
- **问题**: 竞争对手数千种产品价格的电子表格，3 个员工打印成厚纸分头比对，通常要花几天
- **方法论的使用**: 室友（当时还是编程新手）说「如果你有打印件的原始文件，我会写一个程序来做这件事」，几小时后写出简短程序：读竞争对手价格文件 → 查商店数据库 → 记录谁更便宜
- **结论**: 价值在于把逐项比对换成一次性脚本
- **结果**: 程序实际运行只花几秒钟；室友与同事那天「享受了超长的午餐」

### 案例 2: 数独推理类比（前言）
- **类型**: 书中示例（前言）
- **问题**: 解答数独是否要精通数学
- **方法论的使用**: 数独每解决一行、一列或一个方块，为剩下部分提供更多线索
- **结论**: 「就像解决数独问题一样，编程需要将一个问题分解为单个的、详细的步骤」
- **结果**: 未说明（作者结论，非实验）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这张卡?

1. 要开始一个较大的自动化任务，不知从哪下手（还没有清晰步骤）
2. 想把任务先拆成计划/清单（「程序要做的事」→「代码要做的事」）
3. 想引入新工具/新写法，不确定值不值——先写笨版本对照
4. 已有脚本要迁移到新场景，或项目做完想给成果列可复用的改造方向

## E — 可执行步骤 (Execution)

1. **列「程序要做的事」**
   - 完成标准: 后退一步写自然语言清单（取输入 → 处理 → 输出），暂不写代码
2. **翻译成「代码要做的事」**
   - 完成标准: 每步映射到具体 API（如 pyperclip、正则），逐条标「第 N 步」，用 TODO 注释留进骨架，每步独立可验证
   - 判停条件: 某步映射不出 API → 回步骤 1 拆得更细
3. **先笨后巧**
   - 完成标准: 引入新工具前，先写不用它的笨版本并跑通（如 len()/下标版）
4. **危险动作先预演**
   - 完成标准: 会改动/删除数据前，先注释危险部分或先 print 待处理清单，人工确认后再放开（与 `organize-files` 的流程配合）
5. **完成后列「类似程序的想法」**
   - 完成标准: 2–4 条新用途线索，动词短语起头；需要别的章节能力时显式交叉引用（如「第15 章介绍了定时调度，第16 章介绍了如何发送电子邮件」）

**输入契约**: 必需 = ①任务描述与目标；②有无现成脚本要迁移（有则提供脚本与用途）。缺目标用途先问。
**输出契约**: 两张清单 + TODO 骨架 + 迁移线索清单；完成标准 = 每步可回指 f15 / p74。

## B — 边界 (Boundary) ★

### 不要在以下情况使用这张卡

- 需要工程化的团队项目：测试、版本控制、面向对象设计不在本书范围（p04 取舍的反面）
- 长期维护与协作场景——本书代码是「用完即抛弃」口径
- 任务小到一步可写时先计划是开销；触发词「从哪开始」宽而弱——已明确要做什么、只缺操作时，直接走相应任务卡

### 作者在书中警告的失败模式

- 「很容易想要直接开始写代码」——跳过高层计划的代价：方向性错误后期才暴露（f15 开篇警告）
- 笨版本停在原地：isPhoneNumber「函数有17 行，但只能查找一种电话号码模式」——该换工具时不换，代码又长又难扩展（f13）
- p04 折中的反噬：为「更简单、以便学习」允许全局变量等违反最佳实践——放到长期维护/团队场景就是债

### 作者盲点与底本缺口

- 本单元是唯一跨章汇聚型单元（前言 + 第7章 + 30 处项目末尾）；p04（编码规范）同时是全流水线「为什么不讲风格/测试」的总闸门说明（unit_note）
- 「先笨后巧」对照只适用于「文本模式查找」类任务，书中未把它上升为通用方法论（f13 缺失条件）
- p74 的迁移模板字段是从 30 处「类似程序的想法」实例归纳的（模板字段可在源文核验）
- 测试/版本控制/面向对象不在本书范围（p04 口径）；c01 为转述案例、c03 为类比结论（无数值实验）
