## I — 方法论骨架 (Interpretation)

这张卡把「卡住」变成一条接力流程：先自查、再提问。

自查的适用判据是「错误信息能被检索到」：把错误信息原文（含引号的准确文本）丢进搜索引擎——多数问题别人已经遇到并得到解答；自定义错误信息不可检索，不适用这招。

提问的判据是「帮助者能否复现」——一条合格求助信息要让人不用追问就能动手：① 打算做什么（不只是做了什么，帮助者才能判断你是否走错路）；② 错误发生位置（每次启动就发生，还是某些动作之后）；③ 完整错误信息 + 代码（贴 pastebin / gist 再给链接，避免格式丢失）；④ 已尝试的方法；⑤ Python 版本 + 操作系统及版本；⑥ 改了什么之后开始出错；⑦ 能否重现、哪些操作能重现。

外加「怎么问」的边界（礼节）：不要全用大写提问、不要对帮助者提无理要求——否则信息再全也把「求助」变成「无人理」。

## A1 — 书中的应用 (Past Application)

### 案例 1: 故意制造 TypeError，再拿完整错误信息去搜索
- **类型**: 书中演练（前言）
- **问题**: 证明「独自解决编程问题可能比你想的要容易」
- **方法论的使用**: 交互式环境输入 '42' + 3 故意产生错误，得到含行号与 TypeError 的完整回溯；再把错误信息准确文本（包括引号）粘进搜索引擎
- **结论**: 「你常常会发现，别人也遇到了同样的问题，而其他乐于助人的人已经回答了这个问题」
- **结果**: 书中说明会「看到许多的链接，解释这条错误信息的含义」；未给搜索结果页面细节

### 案例 2: pastebin / gist 贴代码，作者留下的联系方式
- **类型**: 作者亲历（前言，作者自陈示范）
- **问题**: 帖里直接贴代码会格式丢失；以及去哪问、问谁
- **方法论的使用**: 把完整错误信息和代码复制粘贴到 pastebin.com 或 gist.github.com，再给 URL；作者贴出自己的代码片段为范例，并留下博客与邮箱表示愿意回答提问
- **结论**: 未说明（该节为建议与作者自陈，无实验结果）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这张卡?

1. 脚本报错卡住了：不知道错误什么意思、去哪问、怎么问
2. 想写一条求助信息/issue，希望一次被解答而不是被反问
3. 想学会自查——报错后先搜错误信息原文，再决定要不要提问
4. 发帖前按清单自检（目的/完整错误/已尝试/版本环境）

### 语言信号

- 「这个报错什么意思」「我在论坛怎么问」「该怎么描述我的问题」「贴代码去哪贴」
- 英文: "what does this error mean", "how to ask", "describe my problem", "can someone help me fix"

### 与相邻能力的区分（阶段 3 定稿）

- 与 `debugging-toolkit` 的区别: 两卡构成「自查→求助」先后接力（composes-with）：有明确技术问题要系统排障走那条；本卡处理「问题还没被问清楚」的求助现场

## E — 可执行步骤 (Execution)

1. **先自查：搜错误信息原文**
   - 完成标准: 把错误信息准确文本（含引号）粘进搜索引擎；会读回溯三件套（指令、行号、错误类型）
   - 判停条件: 搜索已解决 → 结束；仍无解 → 步骤 2
2. **整理现场：七要素过一遍**
   - 完成标准: 备齐 目的 / 错误位置 / 完整错误 + 最小代码 / 已尝试 / 版本环境 / 改动 / 可复现——一条不缺
3. **贴完整错误与代码**
   - 完成标准: 完整错误 + 代码放 pastebin.com 或 gist.github.com，帖子里给 URL
4. **按礼节发出**
   - 完成标准: 不全用大写、不提无理要求；发到可提问渠道（书中给 Stack Overlow、learnprogramming subreddit，先查 FAQ）

**输入契约**: 必需 = ①完整错误信息原文（不得截断/截图代替）；②想做什么；③已尝试方法；④Python 版本 + 操作系统。缺任一项先补问，不静默猜。
**输出契约**: 一条可直接发布的求助信息（七要素 + 错误/代码链接）；完成标准 = 逐条对上 f65 / p01，且不含 ce01 拦下的三类问题（不说目的、错误截断、全大写）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用这张卡

- 已有明确技术问题要做系统排障——那是 `debugging-toolkit` 的场景，两卡先后接力
- 自查已解决问题时（无需提问）
- 渠道有既定模板/FAQ 时——先按渠道要求整理

### 作者在书中警告的失败模式

- ce01 三类翻车姿势：不说目的（帮助者不知道你是否走错路）、不给完整错误与版本环境（无法复现，只能猜）、全大写与无理要求（让人不回应）——「求助」变「无人理」
- 危险征兆（ce01）：只贴代码或只描述现象不写想做什么；只贴一部分错误或用截图代替可复制文本；全大写催问

### 作者盲点与底本缺口

- 本单元来自前言（对应 task-20）；f65 与 p01 内容高度重合（同一清单的两个视角），本卡合并叙述（unit_note）
- 渠道是 2015 年的社区形态；OCR 把 Stack Overflow 印成 Stack Overlow（引文照抄）
- 自定义错误信息不可检索，p03 的「先搜」对其不适用
- 现代问答渠道（含 AI 助手）不在书内——渠道惯例按当前情况核对

### 容易混淆的邻近方法论

- `debugging-toolkit`: 「自查→求助」接力——先按调试卡自查，卡住再按本卡构造求助信息
