# 三级解法：改结果、改原因、改模型（流程·制度·系统）

## R — 原文 (Reading)

> 制度，是规定，是契约，关注的是结果；流程，是基于时间线做一件事的过程，关注的是过程；而系统，是内部各个要素、变量之间相互关系、相互作用的整体，关注的是各要素之间的关系。…改变制度是改变结果，改变流程是改变原因，改变系统则是改变模型。……
>
> 解决问题的办法有1000种，但最有效的那一个，一定是用洞察力改变模型、改变系统。
>
> — 第2章 思考问题的底层逻辑 · 流程、制度与系统（L1149-1262、L1259-1261）

## I — 方法论骨架 (Interpretation)

一个问题到手，先问它的**根本解在哪一层**。三个词各管一段：**制度**管结果（规定、契约——不允许行贿、家属不能在同一个部门，都是刚性的）；**流程**管过程（基于时间线做完一件事的整个过程：把大象装进冰箱三步）；**系统**管关系（内部各要素、变量之间相互作用的整体——分粥人与粥、碗的关系）。

对应三级解法：**改变制度是改变结果，改变流程是改变原因，改变系统则是改变模型**——「普通的人改变结果，优秀的人改变原因，顶级优秀的人改变模型」。

层级的价值在诊断：分粥问题先后试过选一名德高望重的和尚、轮流分粥、成立分粥委员会与监督委员会——全在换人/轮换/加监督上打转，全部失败；最后的解法只改了一处关系：**先把粥分到每个碗里，分粥人最后拿**——分粥人若分得不公平，自己就得挨饿，利益与公平绑定，问题消失。降落伞质检同理：不加重处罚、不加派人力，只让厂家负责人亲自跳伞。

两条边界先记下：**制度是为了避免大事故，不是创造成功**（它是红绿灯、是护栏）；改变流程、制度是**管理**，改变系统、模型是**治理**——顶级优秀的人，用治理的方式管理组织。

## A1 — 书中的应用 (Past Application)

### 案例 1: 和尚分粥
- **类型**: 书中演练（第2章）
- **问题**: 一桶粥每天分得不公平，负责分粥的人碗里的粥总是又稠又多
- **方法论的使用**: 方案递进——①选一名德高望重的和尚分粥（并未改变，还出现腐败：有人贿赂）；②轮流分粥（轮到谁，谁给自己多分）；③成立分粥委员会和监督委员会（意见不一致，吵来吵去，粥都凉了还分不了）；④轮流分粥、先把粥分到每个碗、分粥人最后拿。前几种改的是人与监督方式，最后一种改的是「人—粥—碗」的关系
- **结论**: 最后一种才是根本解——「本质上，是改变前几个流程中人与粥、碗之间的关系」；分粥的那个人如果分得不公平，自己就得挨饿
- **结果**: 每天的粥都分得特别公平

### 案例 2: 二战降落伞：让厂家负责人跳伞
- **类型**: 书中转述（第2章）
- **问题**: 二战期间，美国空军降落伞的合格率是 99.9%——每一千个跳伞的士兵中，就会有一个人因为降落伞的原因丧命；军方要求必须达到 100%，厂家负责人罗列理由称他们已经竭尽全力
- **方法论的使用**: 是改变制度（严厉处罚），还是改变流程（用更多人力检测）？都不需要——军方改变了检查系统：每次交货前，随便挑几个降落伞，让厂家负责人亲自跳伞检测
- **结论**: 这是「改变系统、改变模型」的典型——顶级优秀的人用治理的方式管理组织
- **结果**: 从此降落伞的合格率达到了 100%

### 案例 3: 把大象装进冰箱的流程
- **类型**: 书中演练（第2章）
- **问题**: 什么是流程？
- **方法论的使用**: 作者示例——第一步，打开冰箱门；第二步，把大象装进冰箱；第三步，把冰箱门关上（流程是线性的、连贯的、客观的）
- **结论**: 「凡事皆有流程，只是效率有高低之分」——流程管理与优化，都是为了更高效率地完成某件事而进行的改变
- **结果**: 未说明（概念示例）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 同一个问题反复出现，换人、加监督、抓执行都不根治
2. 需要在「改制度、改流程、改系统」之间做选择，不确定动哪一层
3. 想评估眼前方案是治标还是治本，值不值得推动
4. 设计机制/规则时，想把「人的自利」与「制度目标」绑在一起
5. 复盘时想回答：这次的改动，到底改了哪一层

### 语言信号

- 「这个问题为什么总是反复出现？」
- 「换个靠谱的人来管，行不行？」
- 「再加一条规定/加个流程/成立个委员会吧」
- 「怎么设计一个不靠自觉也能运转的机制？」
- 英文: "root cause vs symptom", "fix the system, not the people", "incentive design"

### 与相邻 skill 的区分

- 与 `hypothesis-verify-adjust` 的区别: 那条决定「怎么验证」（假设→验证）；本 skill 决定「在哪一层动手」（结果/原因/模型）
- 与 `system-five-blocks` 的区别: 本卡的「改变模型」以看穿系统结构为前提——先用 `system-five-blocks` 看清连接关系，再选层级
- 与 `no-kpi-management` 的区别: 改变模型在管理场景的一种应用是机制设计——本卡给「动哪一层」的判断，`no-kpi-management` 给「怎么设计」的展开

## E — 可执行步骤 (Execution)

1. **问题定级**
   - 完成标准: 判断当前问题与候选解法各处在哪一层——结果（制度/规定）、原因（流程）、模型（系统/关系）；写下一句「要改的是 X 层」
   - 判停条件: 只拿到现象、看不清关系的 → 先转 `system-five-blocks` 做结构分析，再回来定级

2. **检查根本解**
   - 完成标准: 对候选解法自问「改了它，问题会不会换个形式回来」；会回来的，层级不够
   - 输出契约: ①现象 ②三层候选解法 ③根本解所在层

3. **设计模型解法（权限允许时）**
   - 完成标准: 找出应改变的关系（谁的利益与什么绑定），给出「分粥人最后拿」式的机制改动
   - 判停条件: 权限不足且无法提交 → 明确降级到可行层执行，并标注「系统层解法未落地」，不空谈越级

4. **复核**
   - 完成标准: 过三问——①有没有改这一层的权限与前提？②是否治本（问题会不会复发）？③是否用「改模型」否定了必要的执行动作？
   - 输出契约: ①定级结论 ②解法与层级 ③权限与前提说明 ④执行动作清单（不得悬空）

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 把「顶级优秀的人改变模型」当越级指南：改模型需要权限与前提，普通人多在结果层——先在权限内做对，再积累改模型的条件
- 用「改模型」否定执行的价值：再好的模型也要落到流程与执行，层级高不等于动作可以悬空
- 层级判断需要证据：没有证据就升格为「系统问题」，是把简单问题复杂化——先做结构分析（配合 `system-five-blocks`），再定级

### 作者在书中警告的失败模式

- 在制度/流程层反复用力：分粥的前几种解法（选人→腐败、轮换→自利、加委员会→争吵）全部失败——不改变利益结构，换谁都不行（ce103）
- 把制度当成功引擎：「企业之所以制定这些制度，不是因为它们能使公司获得成功，而是为了避免公司出现大事故」——制度是红绿灯与护栏，别指望靠加制度赢（p41）
- 结果层救火不治本：降落伞案例中，书里设问「是改变制度，严厉处罚，还是改变流程，用更多人力检测？都不需要」——前两层解法对这个问题的复发无效

### 作者的盲点 / 时代局限

- 行动者假设：三级解法预设读者是能拍板改系统的人；对执行者、无权限者，书中未给「改不动时怎么办」的完整路径（立场盲点：商业顾问视角）
- 证明强度不足：分粥是寓言、降落伞是转述的经典故事，「改模型→问题消失」由叙事呈现，非可核实的经营数据；书中未给改造失败或改完反弹的反例
- 成本与阻力未讨论：改模型的重构成本（组织阻力、过渡期混乱）未被展开——「最有效」不等于「最可行」，作者未做这一步区分

### 容易混淆的邻近方法论

- `hypothesis-verify-adjust`：先验证再动手 vs 先定级再动手；两卡可串联——验证发现根在模型层，就转本卡定级
- `no-kpi-management`：本卡是「在哪层改」的判别框架；`no-kpi-management` 是「改变模型」在管理场景的一种具体应用（机制设计）
- 「加制度就能管住」的默认做法：制度治标、且只为防大事故；把治标当治本是本卡最常见的误用
