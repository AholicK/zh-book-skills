# 书籍蒸馏 → Skill 生产流程手册

> 版本：v1.0 · 2026-09-20
> 依据：26 本 OCR 中文书 → **25 个可执行 skill / 539 张能力卡 / 9.4 MB** 的完整实做
> 流水线：`cangjie-skill` RIA-TV++ v2.5（`--output single`）
> 环境：一台 Linux 云主机（SSH 可达）+ hermes/WorkBuddy；本地只做同步与文档
>
> 📌 **定位：速查版**。完整方法论见 `怎么做skill-从一本书到可调用的能力.md`（**§八 已并入本册的问题清单**），
> 分步操作见 `自己做第一个skill-实操清单.md`。本册重点是**「照着做」的流程 + 全部坑**。

**这份文档解决两个问题**：① 下一批书怎么照着做；② 这次踩过的坑怎么不再踩一遍。
§5「问题清单」是本文档最有价值的部分——**本次 90% 的返工都源于其中的可预防项。**

## 0. 适用边界（先确认再动手）

| 适用 | 不适用 |
|---|---|
| 方法论/自我提升/技术类书籍（有可执行步骤） | **小说**（如《伊豆的舞女》）——没有方法论可蒸馏 |
| 中文 OCR 全文（`.md`，14 MB / 616 万字量级） | 已经结构化好的「九段式知识文档」——那是**另一个项目**的产物，别当输入 |

**⚠️ 两种「书的文本」必须分清**（混过一次）：

| 目录 | 内容 | 用途 |
|---|---|---|
| `书籍/markdown/` | OCR 全文，26 本，14 MB | **本次的输入** |
| `书籍/知识文档/` | 九段式摘要，26 本，1.8 MB | 另一个已完成项目的产物，**不是输入** |

文件名一一对应，极易认错。**动手前先 `du -sh` 与 `wc -c` 核对量级。**

## 1. 开工前必须拍板的 6 件事

1. **书目与排除项**：逐本确认「有没有方法论」。小说、纯文学作品直接排除。
2. **输出模式**：**一律 `--output single`**（一个 skill + N 张能力卡）。`pack` 模式已试水否决。
3. **跑在哪里**：云服务器 + hermes。**不在本地**——本地跑 23 本不现实。
4. **预算口径**：**上传免费、回传计费**（云厂商出方向流量约 3 元/GB）→ `书籍/原始PDF/` 648 MB **一律不回传**。
5. **跑批参数**：超时 A/B/C = **5400 / 3600 / 5400 s**；`WORKERS=2`、`MAX_PASSES=2`。
6. **源文本口径**：见 §0，核对量级。

## 2. 七阶段流程（严格按顺序）

`cangjie-skill` 的 RIA-TV++ 流水线。每阶段的**产出**与**卡点**：

| 阶段 | 做什么 | 产出 | 本次卡点 |
|---|---|---|---|
| 0 | 源文本分块与索引 | chunks / index | 大书分块耗时长，注意超时档位 |
| 1 | 候选能力单元 harvest | 候选清单（每单元 9 条候选） | 候选过多会拖慢后续，靠 `skill_budget` 收敛 |
| 1.5 | 引文回源核验 | 引文账 | **本次的 40 个百分点差全是判据缺陷**，见 §5-B |
| 2 | 单元定稿（R / I / A1 / A2 / E / B 六段） | 能力卡 `.md` | 卡片的 B 段（边界）最容易被写窄 |
| 3 | 编译成 skill（`--output single`） | `SKILL.md` + `references/` | — |
| 4 | 输出层用例 + 触发层套件 | `test-results.md`、`trigger-suite.json` | 套件自带**卡级**真值，别当系统级用（§5-B 坑 3/8） |
| 5 | 收尾与入库 | `BUILD_MANIFEST.json` | 手改产物必须写 `local_patch`，见 §6 |

**跑批监控**：每本完成会落 `.RESCUED` 之类的残留标记，收尾时必须**清零**。

## 4. 跑批后的四道体检（本次最大增量）

流水线自带的测试是**书内**的（负例取自同书相邻卡），**从不测跨书仲裁**。所以这四道必须自己补。

### 4.1 引文回源核验 → **99.8%**

1729 条引文命中 1725，20 本 100%，4 条未命中**全部可解释、无编造**。
⚠️ 初版只有 59.6%，**40 个百分点全是判据缺陷**（跨行拼接、水印切句、口径太窄），见 §5-B。

### 4.2 书级路由体检 → 命中率**不是**质量指标

146 条真实题面 × 25 候选 × 六轮。按「题面出处」判分只有 **50.9%–61.6%**，但**逐条回读后落点几乎都能接住问题**——机制是**同域多书**（Python 三本、心理三本、思维模型三本）。

**判据**：先看 `none` → 再看稳定碰撞的接盘方有没有对应能力卡 → **最后才看命中率数字**。
逐条一致率只有 ~80%，**单轮采样不可解读，只看稳定碰撞（≥2 轮同落点）**。

### 4.3 卡片层核验 → **98.8%**（此前完全没测过的一层）

落对了书、**书内选错卡**同样会让用户拿到似是而非的答案。用套件自带的 `expected_target` / `trap_for` / `accepted_targets` 判分，把**该包自己的 SKILL.md** 交给模型让它选卡。

| 用例类型 | 通过率 |
|---|---|
| `trigger` 应触发指定卡 | **100%**（276/276） |
| `global` 应答「本包没有合适的卡」 | **100%**（46/46） |
| `trap` 须避开诱饵卡 | **97.1%**（134/138） |
| `edge` 边界可接受集合 | **95.7%**（44/46） |
| **合计** | **98.8%**（500/506） |

→ **「书内选错卡」这个担心实测不成立**。最弱的是 `trap`（「表面像 A 实为 B」）。
⚠️ **不要合成「端到端命中率」**——书级与卡级是分层独立测量、取样不同，乘起来是假数字。

### 4.4 答案质量双盲 → **必须左右各判一次**

「命中率不是缺陷率」这个结论只验证了一半（接盘方**有**卡），还得验证**接出来的答案一样好**。

方法：稳定碰撞抽样 → 两臂各生成一份答案 → 匿名化 → 裁判盲评三维度 → **交换左右再评一次** → 合并判分。

→ 详见 §5-C：**只判一次会得出假结论**。

## 5. 问题清单（本次踩过的全部坑）

### A. 产物缺陷类 —— 3 处**同型**安全缺陷（最严重）

**症状**：自伤/轻生、家暴/人身安全的题面，在 25 候选系统里被答 **`none`**——`none` 是唯一真正有害的失败模式，不是「路由到隔壁书」，而是**一条转介路径都没有**。

**根因（三例完全同型）**：`description` 里的笼统排除句**把自家已有的安全卡锁死了**。

| # | 卡 | `description` 写了什么 | 而规格其实写在哪 |
|---|---|---|---|
| 1 | `siddhartha::crisis-anchor` | 「不适用于…自伤风险」 | 该卡逐字覆盖「想消失／想睡过去」，E1 就是安全分级判停 |
| 2 | `counseling-for-toads::depression-warning-signs` | 「不适用于…危机干预」 | 该卡三步齐全，A2 原句列出了那两条测试题面 |
| 3 | 同上（家暴/人身安全） | 「不适用于…正在发生的虐待与暴力处置」 | **`SKILL.md` 正文**「边界与判停」段早就写着「停止本流程，先确保安全并转介专业机构」 |

**⚠️ 教训**：修的方向必须是**让实测行为回到流水线自己写下的规格**，不是我去覆盖流水线的判断。
**⚠️ 修的时候自己又踩的坑**：第一版把急性情形写成「本 skill **不做**急性处置」→ 路由读成**排除条款** → 最急的题面出现 `none`。

**验证结果**：4 条家暴用例 **8/8 归位**，危机专项 25 条 `none` 只剩规格本就要求的 2 条，全量 146 题 `none` 归零。

### B. 审计口径十坑（**每次**都得出过假结论）

**铁律：凡「脚本统计出的缺失／相似／失败／低命中」，下结论前必须回读被判定有问题的那条本体——包括它用到的每个字段的定义。**

| # | 坑 | 假结论 → 真相 |
|---|---|---|
| 1 | 断言**措辞**缺陷伪装成内容缺陷 | — |
| 2 | 只扫 `regex` 漏掉 `json_equals` 表达的转介要求 | 「72 个危机题面中 53 个无转介」→ 实际 13 个真候选全过 |
| 3 | n-gram 算重叠 | `hourly-rate-time` 与 `python-quick-reference` 因共有 `howto`/`time` 被判相似 |
| 4 | 把「题面出处」当「正确答案」 | 50.9% 被误报成「11 个 skill 路由全错」 |
| 5 | 引文跨行拼接 | — |
| 6 | OCR 水印行切断句子 | — |
| 7 | 把 `expected=sibling`（同书另一张卡）当成「不应落本书」 | 产生假 `!!` |
| 8 | **把卡级字段当系统级字段** | `expected_target=none` = 「本 skill 里没有卡该接」，**不是**「系统应回答 none」→ 据此误判「语料政策矛盾」 |
| 9 | **只扫 `description` 一层就定性** | 把「自锁缺陷」误判成「能力缺口」（救命规格写在 `SKILL.md` **正文**判停段，关键词一个都搜不到） |
| 10 | **盲评 A/B 只判一次** | 见 §5-C |

**推论（查「有没有人承接某话题」必须三层都读）**：
`description`（路由层）→ `SKILL.md` 正文判停段（行为规格层）→ 能力卡 A2/E/B 段（判停层）。**只读一层必出假结论。**

**记账铁律**：统计要**分桶打印**（如 `by_kw` / `by_meta`）。本次把元数据桶的 13 当成危机专项总数，**连写了三轮**；同一轮还把「无一本 0 分」写成了结论，实际 r3/r5/r6 各有一本单轮 0/6（采样产物，不是死技能）。

### C. 实验设计类 —— 盲评的**位置偏差**（8:4 是假的）

**现象**：首轮 12 组双盲，裁判**选 A 10 次 / 选 B 2 次**，而出处方放在 A、B 位是**均衡的（6/6）**。
→ **左右随机化均衡 ≠ 位置效应被消除。** n=12、每侧 6 条时，「出处方更优」与「左位更优」**根本无法分离**。

**做法**：同一批答案**交换左右顺序再盲评一次**（提示词不变），合并成 24 次判定、左右各 12 次。

| 指标 | 结果 |
|---|---|
| 左位胜率 | **17/24 = 70.8%** |
| 来源胜负（平衡后） | 出处方 **13 : 11**（p = 0.84） |
| 分层 | 出处方**在左胜 75%**、**在右胜 33%** —— **镜像对称** |
| 纯位置模型预测 | 8.5 / 3.5，**实测 9 / 4** —— 几乎重合 |

→ **数据只需「位置效应」就能解释，不需要引入「来源效应」。**
→ **凡盲评 A/B 类评测（两两比较、偏好标注），必须每个样本左右各判一次。**
→ 订正后措辞：**「既没检出接盘方更差，也没检出出处方更好，两边基本等价」**（且有 3 组接盘方反而稳定更优）。

### D. 环境 / 工具类

| 坑 | 症状 | 做法 |
|---|---|---|
| **哈希·分隔符** | GNU `hash␣␣path` vs Git-Bash `hash␣*path`，直接 `diff` 把 645 行全判为不同 | `cut -d' ' -f1` 取 hash 自己拼统一格式，`LC_ALL=C sort -k2` |
| **哈希·换行符** | `published_hashes` 在 LF 算，Windows 是 CRLF → 直接 sha256 **24/24 全不符** | 先 `raw.replace(b"\r\n", b"\n")`；**「整批哈希不符」≈ 系统性编码差异，不是内容损坏** |
| **unquoted heredoc 吃反引号** | `<<PY` 不加引号时，正文里的 `` `code` `` 被 shell 当命令替换执行 → 写入 JSON 的文本丢失全部代码标识符 | **含反引号的脚本一律用文件写再执行，或用 `<<'PY'`** |
| **Edit 工具报成功但未落盘** | 改 `version` 行、长 `description` 首句时各发生一次 | **改完关键元数据必须 grep 回读确认**，不能信「Updated successfully」 |
| **`cut -c` 截断中文** | 按字节切 UTF-8，输出整片乱码 | 中文内容用 Read 工具读，别 `cut -c` |
| **tar 流不能解两次** | 一次 tar 流只能解一次 | 要解两处就先解一次再服务器内 `cp -r` |
| **备份留在技能目录** | 污染文件数（本应 26 个） | 备份直接写进交付目录，不放技能目录内 |

### E. 产物一致性与交付运维

- **五处同步**：本机 skills / 本机 hermes / 服务器 skills / 服务器 hermes / 发布目录，**逐处核对 md5**。
- **手改已发布产物会打破 `published_hashes`** → 必须追加 `local_patch`（date / scope / reason / detail / **`original_sha256`** / applied_by）+ 更新该文件哈希。
- ⚠️ **二次打补丁时 `original_sha256` 必须保留最初值**（不能记成上一次补丁后的值）。
- `bundle_sha256` 未重算时，必须在 `local_patch.detail` 里披露。
- 收尾前跑 `validate_skill_pack.py`，要求 **0 error / 0 warning**。

## 6. 修产物的铁律

这几条每一条都是踩出来的：

1. **划边界，不要删约束。**
   补 12356 热线时，卡里有 NR-05「不编造机构/热线/药物」。删掉它就能补——但会造出**新的内部自相矛盾**。
   正确做法：**NR-05 禁止的是「编造书中没有的内容」**（就医阈值/药物/地方机构/本地热线）；
   12356 是**可核查的公开事实**，既非本书内容也非本地机构 → 标为**唯一例外：可且应当告知，必须标注来源，不得由此推断任何地方热线**。NR-05 本身**未改**。

2. **路由契约写「X 时仍然选我，但第一产出换成 Y」，禁止写「不做 X」。**
   写「不做 X」会被模型读成「X 时别选我」→ 最急的题面答 `none`。

3. **只修发起方那一侧**（触发词最宽、无实测触发率可回归的那本），加显式让位清单，**不动卡片内容**。

4. **双向碰撞（A↔B 互抢）= 同域多书，改 `description` 治不好**，只能出消费侧速查表。

5. **改了 `description` 就必须重跑回归**，并专门查两件事：①目标用例是否归位 ②**有没有过度外扩**（该 skill 抢别人题目的次数有没有上升）。
   本次热线补丁：接单 **33/50 → 33/50（零外扩）**、`none` 3→2 次，逐条落点仅 1 条变化。

6. **端到端冒烟不能省**：改完真跑一遍「加载 SKILL.md → 选卡 → 加载卡 → 生成答案」，
   确认关键产出真的出现（如 12356 带来源标注），且原有顺序没乱（暴力题面第一产出仍是「离开现场/报警 110」）。
