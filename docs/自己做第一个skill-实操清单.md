# 自己动手做第一个 Skill —— 实操清单

_2026-09-20 · 配套阅读：`怎么做skill-从一本书到可调用的能力.md`（那篇讲**为什么**，这篇讲**怎么敲**）_

> **前提**：本机已装 `cangjie-skill`（如 `~/.workbuddy-ai/skills/cangjie-skill/`），
> 且源书文本已在手（本项目是 OCR 全文 markdown，路径按自己的机器定）。

---

## 第 0 步：先破除一个预期 —— **没有「一键出结果」的命令**

这一点必须先说清，否则你会一直找那条不存在的命令。

```
$ cangjie.py --help
cangjie.py — 仓颉统一薄 CLI（路线 C：只做编排与确定性操作，蒸馏仍由 Agent 完成）。
  compile    Capability Bundle → single | compact pack
  eval       分发到触发评测（默认）或输出评测
  ...
`compile` 的输入必须是已验证 Capability Bundle；本 CLI 不声称能从原始书籍一键蒸馏。
```

**分工是这样的**：

| 谁 | 干什么 |
|---|---|
| **你 + Agent** | 读书、提取候选、验证、写能力卡 —— **阶段 0～3 全靠这个** |
| **CLI** | 编译、评测分发、校验、快照回滚 —— **阶段 5 及之后的确定性操作** |

所以「做 skill」本质上是一件**需要判断力的活儿**，CLI 只负责把已经想清楚的东西机械地固化下来。
**别指望敲一条命令就出一本书的 skill** —— 那个东西不存在。

## 第 1 步：环境自检（1 分钟）

```bash
cd "~/.workbuddy-ai/skills/cangjie-skill"
python scripts/cangjie.py doctor
```

实测输出：


- `doctor: PASS` 就可以开工。

## 第 2 步：选书 + 确认三件事

### 选第一本练手书

**别一上来挑大部头。** 按源文件体量排：

| 推荐度 | 书 | 体量 | 为什么 |
|---|---|---|---|
| ⭐ **首推** | 让时间陪你慢慢变富 | **158 KB** | 体量最小 + 方法论清晰 + 可操作 |
| 次选 | 往里走安顿自己 | 227 KB | 偏修养，边界要写细 |
| 次选 | 蛤蟆先生去看心理医生 | 228 KB | 叙事外壳 + 心理方法，适合练「边界」 |
| ⚠️ 别碰 | 社会心理学 | 2664 KB | 需要分块读，是终局不是起点 |
| ⚠️ 别碰 | 计算 / 思考快与慢 | 1.1 MB / 946 KB | 同上 |

### 开工前必须确认三件事

1. **文本来源**：路径写死。**不要凭记忆蒸馏** —— 没有文本就停下来要文本。
2. **元信息**：书名 + 作者 + 出版年（用于目录命名与审计）。
3. **使用目的**：自己学习查阅 → 选 `single`；要接进工作流 → 选 `pack`。
   **不确定就选 `single`**（single-first 原则）。

> 本项目 24 本**全部用 `single`**。`pack` 模式试过一次后被否决
> ——它会把一本书拆成 19 个平级 skill，散得没法用。

## 第 3 步：阶段 0 —— 整书理解

**做什么**：通读，按 Adler 四步（结构 / 解释 / 批判 / 应用）梳理全书骨架。

**产物**：`books/<slug>/BOOK_OVERVIEW.md`

**检查**：能不能用三句话说清「这本书回答什么问题、怎么回答的、凭什么」。

**⚠️ 阶段 0 有一步不能省**：把骨架给用户确认（「我理解对了吗？有没有你希望重点突出的方向？」）。
跳过这一步，后面 5 个提取器会一起跑偏。

---

## 第 4 步：阶段 1 —— 5 个提取器并行抽候选

**做什么**：并行派 5 个子任务，各读一份提取器 prompt，各自产出候选。

| 提取器 | 抽什么 |
|---|---|
| 框架提取器 | 决策框架 / 思维模型 / 流程 / 排障 |
| 原则提取器 | 原则 / 清单 / 规则 / 计算口径 |
| 案例提取器 | 书中实例、例题（标明类型） |
| 反例提取器 | **书中警告的失败模式**（最容易被漏，但最有用） |
| 术语提取器 | 关键概念词典 |

**产物**：`books/<slug>/candidates/<type>.md`

**检查**：**覆盖率硬门** —— 拿候选对照阶段 0 列出的「原书关键任务清单」，
重要任务必须**有候选且有明确去向**。有说不清去向的遗漏 → 补读或退回全量扫描，**不许虚报零遗漏**。

> **反例提取器别省。** 「书中警告的失败模式」直接对应能力卡里的「不适用于」段，
> 这是后面写边界时唯一的素材来源。

---

## 第 5 步：阶段 1.5 —— 三重验证（这一步决定质量下限）

**做什么**：对每个候选跑三道闸门，分流成 `verified / reference / needs_review / rejected`。

| 闸门 | 问的问题 | 淘汰标准 |
|---|---|---|
| **V1 来源充分性** | 能定位到原文、足以支持这个做法吗？ | 找不到原文依据 → 淘汰 |
| **V2 可执行性** | 用合法的新输入能跑通并核验结果吗？ | 只能空谈 → 淘汰 |
| **V3 任务增益** | 能减少遗漏 / 统一口径 / 稳定交付吗？ | 加了等于没加 → 淘汰 |

**产物**：`verified.md`、`coverage-audit.md`、`rejected/`（**淘汰的也要留档**）

**检查**：每个被淘汰的候选都要写明原因。**「为什么不收」和「为什么收」一样重要。**

> ⚠️ **V1 是防编造的唯一防线。**
> 我在做《刻意练习》时以为书里写了「练习要每天 8 小时」——翻遍全书发现**没有**，是我记混的。
> 没有 V1，这种记忆污染会直接进能力卡。

**用户轻确认** ★：把四类结果和重要缺口展示出来再往下走。
**注意**：用户确认**不能替代**来源验证。

---

## 第 6 步：阶段 1.6 —— 晋级门（决定拆不拆成独立 skill）

**做什么**：五条判据，决定某个能力是「晋级成独立 skill」还是「留在路由入口里当一张卡」。

| 判据 | 必需 |
|---|---|
| 独立意图 / 独立契约 / 独立运行 | **前 3 条必须全过** |
| 独立复用 / 独立评测 | 后 2 条至少过 1 条 |

**未晋级 ≠ 淘汰** —— 它保留为来源路由入口内的能力卡。

**默认软预算：8 个可发现入口**（含 1 个来源路由入口）。

> 这一关是为了防「一本书拆成 19 个平级 skill」那种散架产物。

---

## 第 7 步：阶段 2 —— 写能力卡（R / I / A1 / A2 / E / B 六段）

**做什么**：对每个通过验证的单元，写六段式能力卡。

| 段 | 内容 |
|---|---|
| **R** | 原文依据 + 引文 |
| **I** | 诠释 |
| **A1** | 可执行动作（**原书案例与合成演练必须分开标注**） |
| **A2** | 完成判据 + 判停条件 |
| **E** | 输入 / 输出 / 分支 / 完成标准 |
| **B** | **边界**（不适用于什么） |

**产物**：
- `books/<slug>/.cangjie/capabilities/cards/<slug>.md`（**不带 frontmatter**）
- 同时在 `verified.yaml` 登记：`capability_id` / `intents` / `keywords` / `one_liner` / `importance` / `frontmatter.description`

**检查**：**A1 无原书案例时必须如实标注** —— 合成演练不能冒充书中事实。
**A2 不能写虚**：「要用心」这种无法验收的表述不合格。

> ⚠️ **RIA++ 里的 `E` 段和 `B` 段是这套方法最容易被跳过、也最值钱的两段。**
> `B` 段（边界）直接决定 skill 会不会在错误的场景被调用 —— **这比内容写得好不好更影响可用性**。

---

## 第 8 步：阶段 3 —— 建立能力之间的链接

**做什么**：
1. 找出能力间的引用关系，写进 `also_read`，并回填 A2 的「与相邻能力的区分」
2. `candidates/glossary.md` → `GLOSSARY.md`
3. **INDEX / 路由表由编译器从 Bundle 生成，不要手写**
4. `references.md` 里要保留的内容并入 `book/overview.md` 或 `book/glossary.md`

**检查**：**不把待核查内容伪装成可执行方法。**

---

## 第 9 步：阶段 4 —— 压力测试（最容易走过场的一步）

**做什么**：晋级能力**测触发**，router 能力**测可达**。

**关键纪律**：

- **两类都要实际完成代表任务并核对输出** —— **不能用「会调用」替代「做得对」**
- **缺失输出计入评测分母**，未完成**不得声明通过**
- 未过的**回炉重做阶段 2**（不是改断言！）

**检查**：这一步的详细机制见概念文档第二层的「两层盲测」与「三闸门」。

> ⚠️ **本步最常见的自欺**：只跑「触发层」（该不该被加载），不跑「输出层」（加载后答得对不对）。
> 只测触发层，会得到一个「路由很准但回答很差」的 skill，而你看不出来。

---

## 第 10 步：阶段 5 —— 编译与交付

**做什么**：

```bash
# 1. 先生成 DIGEST.md（面向读者的精华长文）

# 2. 编译（auto 会给出推荐模式）
python scripts/cangjie.py compile \
  --bundle books/<slug>/.cangjie/capabilities \
  --out <目标目录> \
  --output auto

# 3. 把决策报告给用户轻确认（按推荐 / 改 single / 改 pack）
# 4. 确认安装位置，复制或 symlink 过去
```

**compile 参数**：

| 参数 | 说明 |
|---|---|
| `--output {auto,single,pack}` | `auto` 给推荐；**本项目一律用 `single`** |
| `--purpose {learning,reference,workflow,distribution}` | 影响编译策略 |
| `--yes` | auto 模式下按推荐直接执行（跳过轻确认） |
| `--force-overwrite` | 丢弃已发布目录中的本地手工修改 ⚠️ 危险 |

**检查**：`python scripts/validate_skill_pack.py` 必须 100% 通过。

---

## 第 11 步：装进 agent 里，用目标系统自己的接口验收

**编译出目录 ≠ 装好了。** 必须用**目标系统自己的接口**验证。

| 平台 | skills 目录 |
|---|---|
| WorkBuddy | `~/.workbuddy-ai/skills/` |
| hermes (Windows) | `%LOCALAPPDATA%\hermes\skills\`（即 `$HERMES_HOME/skills`） |
| hermes (Linux) | `$HERMES_HOME/skills`（默认 `~/.hermes/skills`） |

验收：

```bash
hermes skills list | grep -i <slug>      # 期望：出现且 enabled
```

> ⚠️ **两个真踩过的坑**：
> ① **`hermes skills list` 会截断长名字**（`automate-boring-stuff` → `automate-borin…`），
>    用精确全名 grep 会得到**假阴性**。要用前缀匹配。
> ② **`HERMES_HOME/skills` ≠ 其它工具的 skills 目录**。我曾把 skill 装在
>    `~/.workbuddy-ai/skills/`，而 hermes 读 `$HERMES_HOME/skills` → **hermes 一本都看不见**。

## 质量红线（交付前逐条对）

违反任何一条 → **阻止输出**。

- [ ] 1. 每个能力通过了**全部**三重验证
- [ ] 2. 每张卡都有完整六段；**A1 无原书案例时如实标注**
- [ ] 3. 原文引用 ≤150 字/段（英文 ≤100 词/段）
- [ ] 4. 每个 active 能力在 `destinations.json` 中**恰好一个去向**
- [ ] 5. 晋级 skill 的 `description` 明确了 trigger 条件，且与来源路由入口**互有近邻负例**
- [ ] 6. 编译产物通过 `validate_skill_pack.py`（格式 / 相对引用 / frontmatter 100%）
- [ ] 7. **生成目录只读** —— 检测到本地手改时不得静默覆盖
- [ ] 8. 关键任务覆盖有可追溯去向；**实际输出评测与来源核查分别记录**；
      有重要缺口时只能交付**明确标注范围的草稿**，不能宣称完整通过

### 交付之后还要补的三件事（单本可跳过，一批必做）

流水线自带的触发层测试是**包内**的（负例取自同包相邻卡），**从不测跨包仲裁**。
所以一批做完以后，下面三项是空的，**重跑多少遍流水线都补不上**：

- [ ] **跨包路由体检**：真实题面 × 全部候选 × **两轮以上**。只看两件事——
      有没有题面答 `none`（**最高优先级缺陷**）、稳定碰撞的接盘方有没有对应能力卡。
      ⚠️ 逐条一致率只有 ~80%，**单轮采样不可解读**。
- [ ] **包内选卡核验**：把该包自己的 `SKILL.md` 交给模型让它选卡，
      用套件自带的 `expected_target` / `trap_for` / `accepted_targets` 判分。
- [ ] **答案质量双盲**：稳定碰撞抽样 → 两臂各生成 → 匿名 → 裁判盲评
      → ⚠️ **必须交换左右再评一次**（只判一次会得出假结论，见下）。

**安全题面必须全量核验，不能抽样**——本次最急的一条题面里一个关键词都不匹配，
靠关键词 harvest 会被漏掉。

## 快速排错表

| 症状 | 大概率原因 | 处理 |
|---|---|---|
| 提取器抽出的候选空泛 | 阶段 0 骨架没确认 | 回阶段 0，先把骨架给用户确认 |
| 候选一堆但没几个能执行 | V2 没认真跑 | 回阶段 1.5，逐条问「用新输入能跑通吗」 |
| 编译报 schema 错 | `verified.yaml` 字段缺失 | 对 `schemas/capability-bundle.schema.json` 逐字段查 |
| 编译产物 frontmatter 校验失败 | `frontmatter.description` 没登记 | 回到 Bundle 补字段（**不要手改生成目录**） |
| skill 装了但 agent 不调用 | `description` 的触发条件写得像目录不像人话 | 重写为「用户会说的话」 |
| skill 在不该用的时候被调用 | **缺 B 段（边界）** | 补「不适用于…」，并加近邻负例 |
| 触发层通过但回答很差 | **只测了触发层，没测输出层** | 补输出层盲测 |
| 评测显示「恒失败」 | 可能是**断言措辞缺陷**，不一定是内容缺陷 | **先回读真实产出**，别急着改断言 |
| 目录被自己手改后编译不生效 | 编译器保护机制 | 用 `rollback` 恢复快照，改动走 Bundle |
| **多个包抢同一类问题** | 同域多包，改 `description` 治不好 | 出消费侧速查表（给人看的「默认用哪个」） |
| **某类题面哪个包都不接（答 `none`）** | 🔴 多半是 `description` 的排除句**把自家已有的卡锁死了** | **三层回读**：`description` → `SKILL.md` 正文判停段 → 卡片 A2/E/B 段 |
| 修完「不适用」清单，最急的题面反而变 `none` | 写了「不做 X」，被读成「X 时别选我」 | 改写为「**X 时仍然选我，但第一产出换成 Y**」 |
| 改了 `description` 后别处开始乱 | 过度外扩 | 回归时**专门查该包抢别人题目的次数有没有上升** |
| 补信息与自身约束冲突（如要补热线但卡里写「不编造」） | 直接删约束会造出**新的内部矛盾** | **划边界**：区分「编造书中没有的内容」与「可核查的公开事实」，后者标为例外并注明来源 |
| 哈希整批对不上 | 系统性编码差异（CRLF/分隔符），不是内容损坏 | 先 `replace(b"\r\n", b"\n")`，再 `cut -d' ' -f1` 统一格式 |
| 盲评结果看着一边倒 | **位置偏差**（裁判偏好先读到的那份） | **每个样本左右各判一次**再合并；分层看是否镜像对称 |

## 时间预期（诚实版）

| 书的体量 | 单本耗时（有人盯着） |
|---|---|
| 150–250 KB（如《让时间陪你慢慢变富》） | 数小时 |
| 400–600 KB | 半天 |
| 900 KB 以上 | 一整天起，且要分块读 |

**注意**：本项目是在云服务器上无人值守跑的，单本 8 段流水线里有分段跑满 **90 分钟超时**的情况。
**第一次做，务必挑最小的那本**，先把整条链路走通一遍。

---

## 一句话总结

**做 skill 不是「把书讲一遍」，而是把书翻译成一组「什么时候用 + 怎么做 + 怎么算做对 + 什么时候别用」的卡片，
然后闭卷考两次试。**

最容易偷懒、也最致命的三处：**V1 来源验证**（防编造）、**B 段边界**（防误用）、**输出层测试**（防自欺）。
