# 怎么做 Skill —— 从一本书到一个能干活的能力包

_2026-09-20 · 基于「26 本中文书 → 25 个可执行 skill」项目的真实过程与踩坑写成_

> 本文分两层。
> **第一层**用生活化语言 + 一个具体例子讲清「做 skill 到底在做什么」，零基础可读。
> **第二层**用准确术语讲核心机制、适用边界与常见误解，可直接对照工程实践。
> 最后有**术语对照表**、**最容易理解错的地方**、**3 道自检题**。

---

# 第一层 · 小白版

## 一、先说清楚：skill 不是「读书笔记」

大多数人读完一本书是这样的：

> 读完《刻意练习》，记住了三个词：**有目的的练习**、**心理表征**、**走出舒适区**。
> 朋友问你「我练吉他三年没进步怎么办」，你只能说：「你要走出舒适区啊。」

这话没错，但等于没说。**你记住的是结论，不是做法。**

**skill（技能包）就是把「结论」补成「做法」的那份东西。**

打个比方：

| | 是什么 | 打个比方 |
|---|---|---|
| 原书 | 一位老师傅讲了一下午，有故事、有感慨、有跑题 | 一整套口述录音 |
| 读书笔记 | 你从录音里抄了几句金句 | 一页摘抄 |
| **skill** | **把老师傅的手艺整理成一本「照着就能做」的操作手册** | **厨房墙上贴的操作卡** |

关键差别：**操作卡上写的不是「要用心做菜」，而是「客人说要酸的 → 起锅前加醋 15ml → 尝一口，酸度够了就出锅」。**

## 二、一个具体例子：小张和《刻意练习》

小张读完《刻意练习》，想把它变成一个 skill。他的过程是这样的。

### 第 1 步：从书里挑出「能干的事」

**这一步最容易做错。** 新手会去抄目录——「第 1 章有目的的练习、第 2 章大脑的适应能力……」

**错在哪**：目录是「书怎么写的」，不是「读者能干什么」。

正确做法是问自己：**这本书里，有哪几件事是「读者学完可以动手做」的？**

小张从《刻意练习》里挑出了这些：

- 「诊断：我的练习为什么没起作用」（拿四个特点逐条对）
- 「改造：把无效练习改成有目的的练习」
- 「判断：我是遇到瓶颈了，还是方法不对」
- 「破除：怎么回应『我没天赋』这种说法」
- ……

这些叫**能力卡（capability card）**——一张卡 = 一件能干的事。

> 《刻意练习》最后拆出了 **19 张卡**。24 本书加起来 **520 张卡**。

### 第 2 步：每张卡必须回答 4 个问题

这是整件事的核心。**一张卡如果答不全这 4 个问题，它就是不合格的。**

以小张的「诊断练习为什么没起作用」这张卡为例：

**① 什么时候用？（触发条件）**

小张一开始写的是：「想学技能的时候用」。

**太宽了。** 朋友问你「今天晚饭吃什么」，难道也掏这张卡？

改成：「有人说**自己已经练了很久（数月以上）、投入不少，但水平长期没变化**」。
→ 这样 AI 才能在正确的时候把它拿出来。

**② 书里凭什么这么说？（依据）**

必须附上原文位置和引文。**这一条是防止我自己编造。**

小张想写「练习要每天 8 小时」——翻遍全书发现书里**没有**这句，是他记混的。删掉。

> 这一步在项目里是机械校验的：每张卡都必须能回源到原文，查不到依据的候选直接淘汰。

**③ 具体怎么做？（步骤）**

要能照着做。比如：

1. 先问：这个练习**有没有明确的改进目标**？（不是「练一小时」，是「把这段的换把速度提到 120bpm」）
2. 有没有**即时反馈**？（弹错了当场知道，还是练完一周才被发现）
3. 有没有**走出舒适区**？（是重复已经会的，还是在啃刚好啃不动的）
4. 有没有**心理表征**的建立？（能不能说出「这一段理想的听感是什么样」）
5. 四条里有几条缺？缺的那条就是病灶。

**④ 怎么知道做对了？什么情况该停？（验收 + 边界）**

- **验收**：改造后，练一周，看有没有出现「能做到上周做不到的动作」这种**具体的能力增量**。
- **边界**：如果对方有**手部伤病、或者情绪已经明显低落**，这不是练习方法问题 → **停，转专业渠道**。

**这第 4 条里的「边界」，是新手最想不到、也最要命的部分。**

### 第 3 步：合并重复的

书里同一个道理会在五个地方讲。如果老老实实各写一张卡，你会得到 5 张几乎一样的卡。

**必须合并。** 判断标准是「是不是同一件能干的事」，不是「是不是同一句话」。

小张发现「心理表征」在第 3 章、第 5 章、第 8 章都讲了 —— 合并成一张。

### 第 4 步：写总目录

39 张卡摊在桌上，AI 怎么知道该翻哪张？

所以要写一个**入口文件**，说清三件事：

1. 这本 skill 是干什么的
2. **什么情况下该用它**（一句话，要写得能对上用户的话）
3. 每张卡分别管什么，什么情况翻哪张

### 第 5 步：考试 —— 这一步才是真功夫

写完不等于做对。要考两次，而且是**闭卷**。

**第一场考试：认不认得出来？**

准备一批「用户会说的话」，看 skill 该不该接。

- 「我练吉他三年没进步」→ **应该接**
- 「帮我修水管」→ **不该接**
- 「我孩子不肯写作业」→ **该接吗？** 嗯……得看。如果 skill 的触发条件写得太宽，它就会接，然后给出一堆「练习方法」的建议，而对方真正的问题是亲子关系。**这就是失败。**

> 项目里的做法：出 100 多道题，跑 8 轮，看通过率。多数书最后落在 **95.7%–100%**。

**第二场考试：做不做得对？**

同一道题，让两份 AI 各做一遍：

- 甲：**给**它这本 skill
- 乙：**不给**它这本 skill

然后把两份答案的**署名去掉**（变成「甲卷」「乙卷」，评委不知道哪份用了 skill），再按事先写好的**规则**判分。

为什么要蒙名字？**因为如果你知道哪份是自己做的，你会不自觉地偏向它。**

> 项目里的结果：以《底层逻辑》为例，**给了 skill 的 76 题里做对 72 题，没给的 76 题里做对 0 题**。这个差距才说明 skill 真的有用。

### 第 6 步：改 —— 但要小心「改答案」

考试挂了怎么办？这里有个陷阱。

小张发现某道题挂了，第一反应是「把判分规则改松一点，让它过」。

**危险。** 判分规则改松了，这门考试就失去意义了 —— 以后什么都过。

正确做法是**先看真实答案**：

- 如果 AI 其实**答对了，只是换了种说法**（判分规则没覆盖到这个说法）→ **该改规则**。
- 如果 AI **确实答错了** → **不能改规则，要承认这是缺陷**。

> 项目里的真实情况：某本 skill 有 48 条判分规则「永远挂」。
> 逐条读真实答案后发现 —— **绝大多数是 AI 用同义词答对了，但规则没覆盖**。
> 改规则后，48 条全部转正，而那本 skill 的**内容一个字没动**。
>
> 但也有 **4 条**，读了答案确认是**真的没做到** → **一条没改，如实记录为缺陷**。
> 这就是「改判据」和「改事实」的分界线。

## 三、小白版最容易忽略的 3 件事

1. **触发条件比内容更重要。** 内容写得好但触发写歪了，等于一本好书锁在柜子里 —— 或者更糟：**在错误的时候被拿出来用。**
2. **「不适用」必须写。** 一份只说「我什么都能干」的说明书，等于没有说明书。
3. **必须考两次试，且必须闭卷。** 只考「做得好不好」，不考「该不该接」，会漏掉最严重的错误类型。

## 四、哪些书能做，哪些不能

| 能 | 不能 |
|---|---|
| 有**可操作的方法**的非虚构书 | 小说、诗集、散文 |
| 《刻意练习》《高效能人士的七个习惯》《社会心理学》 | 《伊豆的舞女》《百年孤独》 |
| 书里在教你「遇到 X 就做 Y」 | 书里在讲故事、抒发感受 |

**判断方法一句话**：合上书，问自己「**学完这本书，我能多做哪几件具体的事？**」
答不上来的书，做不成 skill —— 这不是技术问题，是内容本身没有可操作性。

> 本项目 26 本书里，有 3 本没做成 skill：《伊豆的舞女》是小说；
> 《非暴力沟通》单独做了试水；《纳瓦尔宝典》单独处理。

# 第二层 · 专业版

## 一、产出物的形态

一个 skill 不是单个文件，而是一个**能力包（capability pack）**：

```
<slug>/
├── SKILL.md                     # 入口：路由契约 + 能力卡索引
├── BUILD_MANIFEST.json          # 构建清单（published_hashes，逐文件哈希）
└── references/
    ├── overview.md              # 全书概览
    ├── capability-index.md      # 能力卡索引
    ├── cheatsheet.md            # 速查
    ├── glossary.md              # 术语表
    └── capabilities/*.md        # 能力卡（R / I / A1 / A2 / E / B 六段结构）
```

**实测规模**：24 本 → 664 文件 / 9.2 MB / **520 张能力卡**（单本 13–39 张）。

### SKILL.md 的 `description` 是路由契约，不是简介

它决定「agent 会不会在正确的时机加载这个 skill」。写法必须是**条件式**：

```yaml
description: |
  当用户想改进任何技能的练习方式时调用：练了很久没进步、卡在瓶颈、不知道怎么练、
  没人教只能自学、坚持不下去、怀疑自己或孩子"没天赋"、担心"年纪大了来不及"。
  覆盖《刻意练习》的全部方法论：……
  不适用于：纯理论探讨、非技能类学习问题的归因。
```

三个要点：

| 段 | 作用 |
|---|---|
| 触发条件（前半） | 用**用户会说的话**写，不是用书的章节名写 |
| 覆盖范围（中段） | 声明这个包里有什么，供 agent 判断粒度 |
| **不适用于（末段）** | 主动排除，防止误触发。本项目 **24/24 全部写了这段** |

### 能力卡的 R / I / A1 / A2 四段结构

| 段 | 含义 | 作用 |
|---|---|---|
| **R** (Reading) | 原文依据 + 引文 | 防编造。是**可回源核验**的锚点 |
| **I** (Interpretation) | 对原文的诠释 | 把书的语言翻译成通用语言 |
| **A1** (Action 1) | 可执行动作 | 「怎么做」 |
| **A2** (Action 2) | 完成判据 + 判停条件 | 「怎么算做对」+「什么时候该停」 |

**A2 是最容易被写虚的一段。** 「要用心」「要坚持」这类无法验收的表述，在 A2 里是不合格的。

## 二、六阶段流水线

| 阶段 | 做什么 | 关键约束 |
|---|---|---|
| **1** 候选提取 | 从原文抽候选能力，按 R/I/A1/A2 组织 | 必须附原文位置 |
| **1.5** 机械核验 | 来源充分性（V1）、归并账、同池去重、结构校验 | **可机械化，不该人肉看** |
| **2** 能力卡写作 | 合并、改写、补边界 | 归并判据是「同一件能干的事」 |
| **3** 编译 | `build_tree()` 生成能力包 + MANIFEST | 逐字节等价比对 |
| **4** 压力测试 | 触发层 + 输出层双盲测 | 见下文 |
| **5** 交付校核 | DIGEST 体检、安装件与受测产物比对 | 证明「装的就是测过的那一份」 |

### 阶段 1.5 的三个机械判据（本项目实际使用的）

1. **V1 来源充分性**：每个候选必须有原文依据，查不到即淘汰。
2. **归并账的引用完整性硬校验**：候选 → 能力卡的映射必须无遗漏、无悬空引用。
3. **同池重复检测**：同一批里重复出现的候选要合并，这是 `rejected` 的主要来源。

> ⚠️ **统计规模必须递归**。`ls | wc -l` 只数顶层，本项目曾把 **503 个文件看成 34 个**。
> 正确写法 `find ... -type f | wc -l`。

## 三、阶段 4 的核心：两层盲测

这是整套流程里最值得理解的部分。「盲」的含义是**判分者不知道自己在判哪一份**。

### 3.1 触发层（routing blind eval）

**问题**：这个 skill 会不会在正确的时机被加载？

- 生成一批用例（本项目单本 100+ 题），分 8 轮跑
- 判分是**机械的**：`selected == expected_target`，不涉及 LLM 判断
- 判分时看不到答案键（blind-roster）

**实测**：《底层逻辑》R4 = **138/138（100%）**；《社会心理学》8 轮 **909/920 = 98.8%**。

> ⚠️ **不要把这个指标和输出层混淆**。曾把某本的「71.3%」误读成触发层通过率 ——
> 那其实是**输出层的区分力比例**（108 条断言中 77 条有区分力）。
> 该本触发层实为 **R4 = 77/77（100%）**。

### 3.2 输出层（output blind eval）

**问题**：加载了 skill 之后，回答是不是真的更好？

流程：

1. **`prepare`**：对每个用例生成多个变体（`new_skill` / `without_skill` / 可选 `old_skill`），
   **随机映射到匿名标签 `vA` / `vB`**，映射表 `mapping.json` 单独存放，不给评审者。
2. **生成**：模型在不知道自己是哪个变体的情况下作答。
3. **`score`**：用**机械断言**判分（先于 LLM judge）。

> ⚠️ **生成阶段是「盲」的，判分阶段是「机械」的。**
> 本项目**全程没有 LLM judge** —— 这一点必须说清，否则会误以为「盲评 = LLM 打分」。

### 3.3 断言（assertion）与四分类

`run_output_evals.py` 支持 7 种 `kind`：

| kind | 含义 |
|---|---|
| `regex` | 正则匹配 |
| `json_equals` | JSON 字段精确相等 |
| `json_number` | 数值容差比较 |
| `json_path` | JSON 路径存在 |
| `contains` / `not_contains` | 子串包含 / 不包含 |
| `file_exists` | 产物文件存在 |

**全批实测分布（4082 条）**：

| kind | 条数 | 占比 |
|---|---|---|
| `regex` | 3565 | 87.3% |
| `json_equals` | 496 | 12.2% |
| `not_contains` | **17** | 0.4% |
| `json_number` | 4 | 0.1% |
| `contains` | 0 | 0% |

把每条断言在 `new_skill` / `without_skill` 两侧的结果交叉，得到四分类：

| 分类 | new | without | 含义 |
|---|---|---|---|
| **区分** | ✓ | ✗ | **真正的判据强度**。有 skill 才对 |
| **恒过** | ✓ | ✓ | 护栏 / 完整性检查。两侧都会做对 |
| **恒失败** | ✗ | ✗ | 双方都没做到 → 疑似断言缺陷或内容缺陷 |
| **反向** | ✗ | ✓ | 有 skill 反而更差 → 断言分支写得过宽 |

> **判据强度看「区分」条数，不看断言总数。**
> 本项目某本修订后：`区分 237 → 294`，而断言总数 349 未变 —— 强度提升了，篇幅没变。

### 3.4 ⚠️ 铁律：官方 scorer 不读修订账

`run_output_evals.py` 的 `cmd_score` **只读 `output_cases[].assertions[]`，
完全不读 `output_assertion_revisions`**。

→ **修订必须落到断言本体上**，修订账只作留痕。

> 本项目踩过：先只写了修订账，重跑 score 后失败依旧挂着。
> 必须从快照回滚，改成直接改 `assertions[].value`，再重跑。

## 四、断言修订纪律：三闸门

修订一条「恒失败」断言时，必须同时通过三道闸门：

| 闸门 | 要求 | 为什么 |
|---|---|---|
| ① | `new_skill` 侧**命中** | 否则改了也白改 |
| ② | `without_skill` 侧**不命中** | 否则从「恒失败」退化成「恒过」，失去区分力 |
| ③ | **`prompt` 本身不命中** | 防止「复述题面」就能蒙混过关 |

**闸门 ③ 不是理论上的谨慎，它真实拦下过断言。**

> 实例：某用例的题面原句就含「给什么建议 / 最容易漏掉什么」。
> 如果采纳那条断言，模型**只要把题面复述一遍就能通过** —— 这是假阳性。
> 闸门 ③ 把它挡下了。本项目共 2 处被闸门 ③ 拦下。

**修订的目标是「恒失败 → 0」，不是「把护栏改成区分型」。**
`恒过` 类断言本就不承担区分职责（它是护栏 / 完整性检查），**应当刻意保留**。

### 诊断口径：是「断言缺陷」还是「内容缺陷」？

**必须先回读真实产出，不能只看统计数。**

| 现象 | 判据 | 处理 |
|---|---|---|
| 产出用**同义不同词**答对了 | new 侧语义正确 | **断言措辞 / 距离窗口缺陷** → 改断言 |
| 产出确实没提这件事 | 读了答案确认 | **内容缺陷** → 不改断言，如实登记 |
| `反向`（new✗ / without✓） | 断言分支过宽 | 收窄分支。典型元凶：`(不(能\|会))` 这种两字宽分支会被 without 侧的通用答法偶然命中 |

**距离窗口是最容易漏的一类**：`A[\s\S]{0,40}B` 里的 `{0,40}` 写小了，产出里 A 和 B 隔了 50 字 → 判失败。
实测某本 57 条修订中，相当一部分只是把窗口从 `{0,20}` 放宽到 `{0,40}`。

## 五、安全覆盖（比「谁更好」更值得测的命题）

### 为什么优先做这个

「A 是否整体优于 B」这个命题：**没有待决决策依赖它**（skill 已交付，没有在选版本），
且成本约 **3,600 次 LLM 判分调用/轮**。

「高风险题面有没有安全兜底」这个命题：**有决策依赖**（安全行为退化时会不会没人发现），
且是**只读脚本、零 LLM 调用**，23 本约 30 分钟。

### 安全要求有三种表达方式（只扫一种会漏两种）

| 表达方式 | 例子 | 硬度 |
|---|---|---|
| ① `json_equals` 必填自检字段 | `$.给出转介并声明缺口`、`$.未建议忍耐` | **最硬**（模型必须显式表态） |
| ② 正向行为 `regex` | `(专业\|精神科\|心理医生\|就医\|就诊\|面诊)` | 中 |
| ③ `not_contains` 护栏 | `别小题大做` | 窄（中文概念词必误伤） |

> **`not_contains` 在中文里只能当护栏**：否定句本身含被否定的词（「不要说『想开点』」里就有「想开点」），
> 所以概念词必误伤，只能选完整建议句。全批仅 17 条（0.4%）是**设计选择，不是疏漏**。

### ⚠️ 镜像教训：审计口径缺陷会伪装成 skill 缺陷

本项目已固化「**断言口径缺陷会伪装成内容缺陷**」。它的镜像同样成立：

> 首版安全审计只扫 `regex` 值里的转介词，于是把以 `json_equals` 表达的转介要求
> **全部判成缺失**，得出「72 个危机题面中 53 个无转介」的**假结论**。
> 修正口径后，13 个真候选**全部通过**。

**通则：凡「脚本统计出来的缺失」，下结论前必须回读被判定为缺失的那条用例的断言本体。**
统计数只能用来**选样**，不能用来**定罪**。

> 🔴 **这个命题在交付后真的抓到了东西**：25 本跑完后做跨包路由体检，查出 **3 处同型安全缺陷**
> ——自伤/轻生 ×2、家暴/人身安全 ×1，全部被答成 `none`（用户什么都拿不到）。
> 根因是 `description` 的排除句把**自家已有的安全卡**锁死了。详见 **§8.3**。

### NR 清单的语义（别误判）

**NR = 必要要求清单，是混合清单，不是纯安全清单。**

实测某本的 NR 构成：NR-05 安全边界 / NR-03 时评限定 / NR-04 OCR 保真度 /
NR-06 分寸 / NR-07 输出测试 / NR-08 特稿转述。

→ 「有的书写了 NR 登记、有的没写」是**留痕风格差异，不是缺陷**。
且 **NR 编号每本书各自定义，绝不能跨书引用**。

## 六、适用边界：什么样的书能做 skill

| 维度 | 适合 | 不适合 |
|---|---|---|
| **文体** | 非虚构、方法论、教材、操作手册 | 小说、诗集、散文、传记 |
| **结构** | 有「遇到 X 做 Y」的条件-动作结构 | 纯叙事、纯抒情、纯思辨 |
| **可验收性** | 能写出「做对了是什么样」 | 只有审美 / 感受层面的判断 |
| **领域** | 认知、心理、时间管理、编程、决策 | 需要实时外部数据才能判断的领域 |

**判据一句话**：**合上书，能否列出「学完能多做哪几件具体的事」。**
列不出来，是**内容本身不可操作**，不是技术问题。

### 反过来：什么任务不该用 skill

- **需要实时数据**（股价、天气）→ 应该接工具，不是写 skill
- **一次性的、不可复用的**任务 → 直接做，不必沉淀
- **纯检索**（「X 是什么」）→ 知识库更合适

## 七、常见误解

| # | 误解 | 事实 |
|---|---|---|
| 1 | 「输出层满分 = skill 很好」 | 满分只是**稳定性下限**。且多数书**未做 train/validation 分离**，题面修订暴露的问题与修订没有区分训练/验证集 → 「满分」的解释力有限 |
| 2 | 「断言越多越严」 | `恒过` 类断言不承担区分职责。**判据强度看「区分」条数** |
| 3 | 「把失败的断言改松 = 优化」 | 那是**把考试改废**。必须先回读真实产出，区分「措辞缺陷」与「内容缺陷」 |
| 4 | 「盲评 = LLM 打分」 | 本项目的「盲」指**生成时不知道自己是哪个变体**；判分是**机械断言**，全程无 LLM judge |
| 5 | 「有区分力 = 答得更好」 | 区分力只说明「有 skill 和没 skill **不同**」，不说明「**更对**」 |
| 6 | 「触发层通过率 = 输出层区分力」 | 两者是完全不同的指标，本项目曾误读（见 §三.3.1 的警告） |
| 7 | 「NR 是安全清单」 | NR 是**必要要求清单**，混合了安全 / 保真 / 方法约束 |
| 8 | 「有 `.RESCUED` 标记 = 交付合格」 | 抢救判据通常只校验最终交付物的哈希，**不校验中间阶段成品**。「抢救入库」≠ 交付合格 |
| 9 | 「skill 装到磁盘上 = 能用了」 | 必须用**目标系统自己的接口**验证（如 `hermes skills list`）。文件在 ≠ 系统认识它 |
| 10 | 「一本 skill 一个 SKILL.md 就够」 | 递归扫描器会把**任何子目录里的 `SKILL.md`** 当成独立 skill。部署前必须模拟扫描 |

## 八、交付之后：四道体检 + 25 本实战问题实录

> 前七节讲的是**单本怎么做对**。这一节讲的是**一批做完之后才会暴露的问题**——
> 全部来自 26 本 OCR 中文书 → 25 个 skill 的实做，**没有一条是单本流水线能测出来的**。

### 8.1 流水线不测的三件事（必须自己补）

流水线自带的触发层测试是**包内**的（负例取自同包相邻卡），**从不测跨包仲裁**。
所以有三大块是空白，重跑多少遍都治不了：

| 空白 | 后果 |
|---|---|
| **跨包仲裁**：一句真实提问最终落到哪个包 | 同域多包互抢；严重时**哪个都不接** |
| **包内选卡**：落对了包，包里选对卡了吗 | 用户拿到似是而非的答案 |
| **落错包的答案质量** | 只能证明「接盘方有卡」，证明不了「接出来一样好」 |

### 8.2 四道体检（实测基线，可直接对照）

| # | 体检 | 做法 | 实测 |
|---|---|---|---|
| 1 | **引文回源核验** | 交付件引文逐条回源文本比对 | **99.8%**（1729 命中 1725，20 本 100%）。初版只有 59.6%——**40 个百分点全是判据缺陷** |
| 2 | **书级路由体检** | harvest 真实题面 × 全部候选 × **两轮以上** | 146 题 × 6 轮；按「题面出处」判分 50.9%–61.6%，**但这不是缺陷率** |
| 3 | **卡片层核验** | 把**该包自己的 SKILL.md** 交给模型选卡，用套件自带 `expected_target` / `trap_for` / `accepted_targets` 判分 | **98.8%**（500/506）。`trigger`/`global` 满分，最弱是 `trap` 97.1% |
| 4 | **答案质量双盲** | 稳定碰撞抽样 → 两臂各生成 → 匿名 → 裁判盲评 → **交换左右再评一次** | 未检出差异（见 8.5） |

**判分顺序（不要跳）**：先看 `none` → 再看稳定碰撞的接盘方有没有对应能力卡 → **最后才看命中率数字**。
逐条一致率只有 ~80%，**单轮采样不可解读，只看稳定碰撞（≥2 轮同落点）**。

⚠️ **不要合成「端到端命中率」**：书级与卡级是分层独立测量、取样不同，两个百分比乘起来是**假数字**。

### 8.3 🔴 3 处**同型**安全缺陷（本次最严重的发现）

**症状**：自伤/轻生、家暴/人身安全的题面，在 25 候选系统里被答 **`none`**。
`none` 是唯一真正有害的失败模式——不是「路由到隔壁包」，而是**一条转介路径都没有**。

**根因（三例完全同型）：`description` 里的笼统排除句，把自家已有的安全卡锁死了。**

| # | 被锁死的卡 | `description` 写了什么 | 规格其实写在哪 |
|---|---|---|---|
| 1 | `siddhartha::crisis-anchor` | 「不适用于…自伤风险」 | 该卡逐字覆盖「想消失／想睡过去」，E1 就是安全分级判停 |
| 2 | `counseling-for-toads::depression-warning-signs` | 「不适用于…危机干预」 | 该卡三步齐全，A2 **原句列出了那两条测试题面** |
| 3 | 同上（家暴/人身安全） | 「不适用于…正在发生的虐待与暴力处置」 | **`SKILL.md` 正文**「边界与判停」段早就写着「停止本流程，先确保安全并转介专业机构」 |

**修的方向**：**让实测行为回到流水线自己写下的规格**，不是我去覆盖流水线的判断。三例**都不需要新增方法论内容**。

**⚠️ 修的时候自己又踩的坑**：第一版把急性情形写成「本 skill **不做**急性处置」→ 路由读成**排除条款**
→ 全语料最急的题面出现 `none`。

> **路由契约的写法铁律**：写「**X 时仍然选我，但第一产出换成 Y**」，
> **禁止**写「不做 X」——后者会被模型读成「X 时别选我」。

**验证**：4 条家暴用例 **8/8 归位**；危机专项 25 条 `none` 只剩规格本就要求的 2 条；全量 146 题 `none` 归零。

### 8.4 审计口径十坑（**每次**都得出过假结论）

> **铁律：凡「脚本统计出的缺失／相似／失败／低命中」，下结论前必须回读被判定有问题的那条本体——
> 包括它用到的每个字段的定义。**

| # | 坑 | 假结论 → 真相 |
|---|---|---|
| 1 | 断言**措辞**缺陷伪装成内容缺陷 | —（§三已展开） |
| 2 | 只扫 `regex` 漏掉 `json_equals` 表达的转介要求 | 「72 个危机题面中 53 个无转介」→ 实际 13 个真候选全过 |
| 3 | n-gram 算重叠 | 两本因共有 `howto`/`time` 被判「相似」 |
| 4 | 把「题面出处」当「正确答案」 | 50.9% 被误报成「11 个 skill 路由全错」 |
| 5 | 引文跨行拼接 | — |
| 6 | OCR 水印行切断句子 | — |
| 7 | 把 `expected=sibling`（同包另一张卡）当成「不应落本包」 | 产生假失败 |
| 8 | **把卡级字段当系统级字段** | `expected_target=none` =「本包里没有卡该接」，**不是**「系统应回答 none」→ 据此误判「语料政策矛盾」 |
| 9 | **只扫 `description` 一层就定性** | 把「自锁缺陷」误判成「能力缺口」（救命规格写在 `SKILL.md` **正文**判停段，关键词一个都搜不到） |
| 10 | **盲评 A/B 只判一次** | 见 8.5 |

**推论——查「有没有人承接某话题」必须三层都读**：
`description`（路由层）→ `SKILL.md` 正文判停段（行为规格层）→ 能力卡 A2/E/B 段（判停层）。
**只读一层必出假结论。**

**记账铁律**：统计要**分桶打印**。本次把某个子桶的 13 当成总数，**连写了三轮**；
还把「无一本 0 分」写成结论，实际是采样产物（每本固定取 6 条，正好全落在同域重叠区就会 0/6）。

### 8.5 盲评的**位置偏差**（8:4 是假的）

**现象**：首轮 12 组双盲，裁判**选 A 10 次 / 选 B 2 次**，而出处方放在 A、B 位是**均衡的（6/6）**。
→ **左右随机化均衡 ≠ 位置效应被消除。** n=12、每侧 6 条时，「出处方更优」与「左位更优」**根本无法分离**。

**做法**：同一批答案**交换左右顺序再盲评一次**（提示词不变），合并成 24 次判定、左右各 12 次。

| 判据 | 结果 |
|---|---|
| 左位胜率 | **17/24 = 70.8%** |
| 来源胜负（平衡后） | 出处方 **13 : 11**（p = 0.84） |
| **分层（决定性）** | 出处方**在左胜 75%**、**在右胜 33%** —— **镜像对称** |
| 纯位置模型预测 | 8.5 / 3.5，**实测 9 / 4** —— 几乎重合 |

→ **数据只需「位置效应」就能解释，不需要引入「来源效应」。**
→ **凡盲评 A/B 类评测（两两比较、偏好标注），必须每个样本左右各判一次。**
→ 订正后措辞：**「既没检出接盘方更差，也没检出出处方更好，两边基本等价」**（且有 3 组接盘方反而稳定更优）。

### 8.6 环境 / 工具坑

| 坑 | 症状 | 做法 |
|---|---|---|
| **哈希·分隔符** | GNU `hash␣␣path` vs Git-Bash `hash␣*path`，直接 `diff` 把 645 行全判为不同 | `cut -d' ' -f1` 取 hash 自己拼统一格式 |
| **哈希·换行符** | `published_hashes` 在 LF 算，Windows 是 CRLF → **24/24 全不符** | 先 `replace(b"\r\n", b"\n")`；**「整批哈希不符」≈ 系统性编码差异，不是内容损坏** |
| **unquoted heredoc 吃反引号** | `<<PY` 不加引号时正文里的 `` `code` `` 被 shell 当命令替换执行 → 写进 JSON 的文本丢失全部代码标识符 | 含反引号的脚本**用文件写再执行**，或用 `<<'PY'` |
| **Edit 报成功却未落盘** | 改长 `description`、版本号时发生过 | **改完关键元数据必须 grep 回读确认** |
| **`cut -c` 截断中文** | 按字节切 UTF-8，输出整片乱码 | 中文内容用 Read 读，别 `cut -c` |
| **tar 流不能解两次** | 一次 tar 流只能解一次 | 要解两处就先解一次再服务器内 `cp -r` |
| **备份留在技能目录** | 污染文件数（本应 26 个） | 备份直接写交付目录 |

### 8.7 修产物的 6 条铁律

1. **划边界，不要删约束。**
   要补 12356 热线，但卡里有 NR-05「不编造机构/热线/药物」。删掉它就能补——却会造出**新的内部自相矛盾**。
   正确做法：NR-05 禁止的是**编造书中没有的内容**（就医阈值/药物/地方机构/本地热线）；
   12356 是**可核查的公开事实**，既非本书内容也非本地机构 → 标为**唯一例外：可且应当告知，必须标注来源，
   不得由此推断任何地方热线**。NR-05 本身**未改**。

2. **路由契约写「X 时仍然选我，但第一产出换成 Y」**，禁止写「不做 X」（见 8.3）。

3. **只修发起方那一侧**（触发词最宽、无实测触发率可回归的那个包），加显式让位清单，**不动卡片内容**。

4. **双向碰撞（A↔B 互抢）= 同域多包，改 `description` 治不好**，只能出消费侧速查表。

5. **改了 `description` 就必须重跑回归**，专门查两件事：①目标用例是否归位
   ②**有没有过度外扩**（该包抢别人题目的次数有没有上升）。本次补丁：接单 **33/50 → 33/50（零外扩）**。

6. **端到端冒烟不能省**：真跑一遍「加载 SKILL.md → 选卡 → 加载卡 → 生成答案」，
   确认关键产出真的出现，且原有顺序没乱（危机题面第一产出仍是转介/求助，不是分析）。

### 8.8 一致性：五处同步与清单补丁

- **五处同步**：本机 skills / 本机 hermes / 服务器 skills / 服务器 hermes / 发布目录，**逐处核对 md5**。
- **手改已发布产物会打破 `published_hashes`** → 必须追加 `local_patch`
  （date / scope / reason / detail / **`original_sha256`** / applied_by）+ 更新该文件哈希。
- ⚠️ **二次打补丁时 `original_sha256` 必须保留最初值**（不能记成上一次补丁后的值）。
- 收尾前跑 `validate_skill_pack.py`，要求 **0 error / 0 warning**。

# 附录 A · 小白说法 ↔ 专业术语 对照表

| 小白说法 | 专业术语 | 说明 |
|---|---|---|
| 一本书拆成一件事一件事 | **候选提取（candidate extraction）** | 阶段 1 |
| 一件能干的事 | **能力卡（capability card）** | 包的最小单元 |
| 卡片上的四段 | **R / I / A1 / A2 结构**（正式为六段 R/I/A1/A2/E/B） | 依据 / 诠释 / 动作 / 判据 |
| 什么时候用 | **触发条件（trigger condition）**，写在 `description` 里 | 决定路由 |
| 什么情况不该用 | **边界声明（不适用于…）** | 防误触发 |
| 怎么算做对了 | **A2 完成判据** | 可验收 |
| 什么时候该停 | **判停条件（stop condition）** | 安全阀 |
| 同一个道理讲了五遍 | **同池重复（duplicate）** → 需**归并（merge）** | 阶段 1.5 |
| 每张卡都要有出处 | **V1 来源充分性** | 机械核验 |
| 总目录 | **入口文件 `SKILL.md` + `capability-index.md`** | 路由层 |
| 整包 | **能力包（capability pack）** | 交付单元 |
| 考试一：认不认得出来 | **触发层盲测（routing blind eval）** | 判 `selected == expected_target` |
| 考试二：做不做得对 | **输出层盲测（output blind eval）** | `new_skill` vs `without_skill` |
| 把署名去掉 | **匿名变体映射（`vA`/`vB` + `mapping.json`）** | 消除评审者偏置 |
| 判分规则 | **断言（assertion）** | 7 种 `kind` |
| 真的有用 | **区分（discriminating）** | new✓ / without✗ |
| 两边都会做 | **恒过（always-pass）** | 护栏类，刻意保留 |
| 两边都不会做 | **恒失败（always-fail）** | 疑似缺陷 |
| 有 skill 反而更差 | **反向（reverse）** | 断言分支过宽 |
| 改规则的三条自检 | **三闸门（new✓ / without✗ / prompt✗）** | 修订纪律 |
| 别把考试改废 | **修订目标是恒失败→0，不是把恒过改成区分** | 核心纪律 |
| 装的就是测过的那份 | **安装件与受测产物逐字节比对** | 阶段 5 |
| 半成品 | **`.RESCUED`** | 抢救入库标记，需复核 |
| 同一批里重复的 | **同池重复检测** | `rejected` 主要来源 |

# 附录 B · 最容易理解错的地方（按危险程度排序）

### ① 「把失败的断言改松」= 把考试改废（最危险）

这是**唯一一个会让整套质量体系失效的错误**。一旦判据可以为了好看而下修，
所有「通过率」数字都失去意义。

**正确姿势**：先回读真实产出 → 判断是「措辞缺陷」还是「内容缺陷」→ 只有前者才改断言。
本项目有 4 条断言，读了答案确认是真的没做到，**一条没改，如实登记为缺陷**。

### ② 以为「统计出来的缺失」就是真缺失

`grep` / 脚本统计出来的「没有 X」**默认不可信**。

本项目两次踩坑：
- 用 `grep -B3 -A8` 的上下文窗口看某用例，看到的是**邻居用例**的断言 → 误判「零危机断言」
- 安全审计只扫 `regex`，漏掉 `json_equals` 表达的转介要求 → 误判「53/72 无转介」

**通则**：判断「某用例有没有某类断言」，**必须按 case_id 精确读取**。

### ③ 把「触发层」和「输出层」的指标混着看

这两个是完全不同的东西：

- 触发层 = 「该不该被加载」（二分类，机械判分）
- 输出层 = 「加载后答得好不好」（断言判分）

本项目曾把某本的「71.3%」（输出层区分力比例）误读成触发层通过率 —— 差了一个量级。

### ④ 以为「描述里写得越全，触发越准」

**触发条件要写得像用户说的话，不是像书的目录。**
写「覆盖第 1–4 章方法论」是无效的；写「练了很久没进步、卡在瓶颈、怀疑自己没天赋」才有效。

### ⑤ 以为「不适用于」是可选的礼貌话

它是**功能组件**。没有它，skill 会在不该用的时候被加载，给出看似合理但答非所问的回答 ——
**这比拒绝回答更糟**。

### ⑥ 以为「写完就能用」

三件事缺一不可：
1. 用**目标系统自己的接口**验证（`hermes skills list` / 平台技能列表）
2. 部署前**模拟递归扫描**（子目录里的 `SKILL.md` 会被当成独立 skill）
3. 长跑任务要 **pin**，否则会被 curator 在 14/30 天未使用时自动归档

### ⑦ 以为「盲评需要 LLM judge」

本项目的盲评是「**生成时匿名 + 判分机械化**」。引入未校准的 LLM judge 会给出**假信心**，
比诚实地说「未测」更糟。

# 附录 C · 3 道自检题（检验你是否真的理解）

### 题 1 · 诊断题

某本书的 skill 在压力测试中，有一条断言显示「**恒失败**」（`new_skill` 和 `without_skill` 都没通过）。
你的第一反应应该是：

**A.** 把这条断言改松一点，让它通过
**B.** 删掉这条断言
**C.** 打开 `new_skill` 侧的真实产出，读一遍，判断是「产出确实没做到」还是「断言措辞没覆盖到产出的说法」
**D.** 重新跑一遍评测，看是不是偶发

<details>
<summary>答案与解析</summary>

**C。**

- A 是最危险的 —— 等于把考试改废。只有确认是**措辞缺陷**时才允许改断言，且必须过三闸门。
- B 是逃避 —— 删掉断言会让判据强度下降，而且掩盖了问题。
- D 是无效动作 —— 恒失败是**系统性**结果（两侧都没过），不是偶发，重跑结论一样。
- C 是唯一正确路径：**回读真实产出**。判据是「产出是否用同义不同词答对了」。
  答对了 → 断言措辞/距离窗口缺陷，可改；确实没做到 → 内容缺陷，**不许改**。

**核心考点**：你能否抵抗「把指标改好看」的诱惑，先去看事实。
</details>

### 题 2 · 设计题

你要给「帮我修一下漏水的水管」这个请求，判断某个《刻意练习》skill 会不会被误触发。
请问：这个判断应该看 skill 的哪个部分？为什么？

<details>
<summary>答案与解析</summary>

看 **`SKILL.md` 的 `description`**（触发条件 + 不适用于段），**不是看能力卡的内容**。

原因：路由决策发生在**加载 skill 之前** —— agent 只能看到 `description`。
能力卡的内容要等加载之后才会被读到。所以：

- 如果 `description` 的触发条件写得像用户的话（「练了很久没进步」），
  而「修水管」对不上 → **不会误触发**。
- 如果 `description` 写得太宽（「想学技能的时候」），就可能在错误时机被加载。

**这正是「触发条件比内容更重要」的工程含义**：内容再好，路由错了就白搭；
更糟的是误触发后给出的回答**看起来合理但答非所问**。

**延伸**：这也解释了为什么「不适用于」段是功能组件 —— 它和触发条件是**同一枚硬币的两面**，
共同定义路由边界。
</details>

### 题 3 · 判断题

有人提出：「既然安全很重要，那应该在每本书的 skill 里都加上几条 `not_contains` 护栏，
越多越安全。」

这个说法对吗？请说明理由，并指出正确的做法是什么。

<details>
<summary>答案与解析</summary>

**不对。** 有三个层面的问题：

**① 技术上：`not_contains` 在中文里会误伤。**
`not_contains` 是子串匹配。否定句**本身含有被否定的词** ——
比如「**不要**说『想开点』」这句话里就出现了「想开点」。
所以概念词一定会误伤，只能选**完整建议句**，且必须逐条实测零误伤。
本项目全批 4082 条断言里只有 **17 条** `not_contains`（0.4%）—— 这是**设计选择，不是疏漏**。

**② 方法上：安全要求有三种表达方式，`not_contains` 是最弱的一种。**

| 方式 | 硬度 |
|---|---|
| `json_equals` 必填自检字段（`$.未建议忍耐`） | **最硬**，模型必须显式表态 |
| 正向行为 `regex`（`(专业\|精神科\|就医)`） | 中 |
| `not_contains` 护栏 | 窄，易误伤 |

正确的做法是**按场景选最合适的表达方式**，而不是机械地加护栏。

**③ 纪律上：「为了指标好看而加断言」本身就是被禁止的动作。**
本项目已有明确纪律：**不要机械地每本补几条护栏凑数**。
「安全」的验证方式是**跨书安全审计**（检查高风险题面是否有转介断言 / 护栏 / NR 登记），
而不是无差别地堆断言。

**正确的做法**：识别真正的高风险题面（自杀自伤 / 暴力侵害 / 医疗越界 / 心理危机），
逐条检查该用例是否具备 ①转介要求 ②护栏，**并回读真实产出确认安全行为真的出现了**。
</details>
