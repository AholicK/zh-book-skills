## I — 方法论骨架 (Interpretation)

编解码与拆分合并都是字符串的**形态转换**，共同点是先声明口径、再动手。

路线一（字符 ↔ 字节）：`encode()` 把字符串转成二进制数据，`decode()` 把二进制数据转回字符串。默认编码 UTF-8，简体中文可显式指定 gb2312，只有一个参数时可省 `encoding=` 直接写编码名。errors 是容错开关，四个取值：strict 遇到非法字符就抛出异常、ignore 忽略非法字符、replace 用「？」替换非法字符、xmlcharrefreplace 使用 XML 的字符引用——**默认 strict**，「默认会帮我兜住」是错的，要容错必须显式改。

路线二（一个字符串 ↔ 一组字符串）：`split(sep, maxsplit)` 按 sep 切开，sep 默认 None 即所有空白字符（空格、换行、制表符），也可指定多字符分隔符；maxsplit 不指定或为 -1 时分割次数无限制，否则结果列表元素个数最多为 maxsplit+1——限制的是「切几刀」而非「切几块」。`join` 是它的逆操作，但**角色容易记反**：调用 join 的那个字符串才是分隔符，被合并的元素在括号里——`string.join(iterable)` 里 `string` 是「合并时的分隔符」，分隔符插在元素之间。

## A1 — 应用示例 (Application Example)

### 示例 1: 按逗号拆开，再用 "-" 拼回去
- **类型**: 合成演练（按原书规则构造，非作者案例）
- **问题**: ①按逗号切成列表；②再用 "-" 合并回一个字符串
- **怎么用**: ①split 必须显式传 sep——默认 None 表示所有空白符，逗号不在其中；②用 `"-".join(列表)`，因为调用 join 的字符串才是分隔符
- **结果**: ①得 3 个元素的列表 `['编号1','编号2','编号3']`；②得 `'编号1-编号2-编号3'`（本项目纸面推演，书中未给示例）

### 示例 2: gb2312 编码往返
- **类型**: 合成演练（按原书规则构造，非作者案例）
- **问题**: 把含中文的字符串用 gb2312 编码后再解码回原字符串
- **怎么用**: encode 指定 `encoding="gb2312"`（书中注明可省 `encoding=` 直接写编码），decode 用同一编码；默认 errors 是 strict，不要指望它自动容错
- **结果**: 解码结果与原字符串相同（书中未给示例，按参数口径推演）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这张卡?
1. 读写文本或对接接口时出现乱码、编码不一致
2. 一批用逗号/分号/竖线分好的字符串要拆成字段
3. 要把列表里的多个字符串拼成一个
4. 不确定 split 默认按什么切、join 该谁写在点号左边

### 语言信号
- 「乱码」「编码不对」「gb2312 / utf-8」「解码报错」
- 「按逗号拆开」「切成字段」「拼成一个字符串」
- 「split」「join」「encode」「decode」
- 英文: "encoding", "decode error", "split a string", "join a list into a string"

### 与相邻能力的区分（阶段 3 定稿）
- 与 `sequence-slicing` 的区别: 切片按**位置**取一段，split/join 按**分隔符**切分与拼装；拆分结果常需再切片
- 与 `file-and-directory-operations` 的区别: open() 的 encoding 与字符串编解码是同一套概念；文件乱码先确认 open 的 encoding，再回到本卡
- 与 `string-formatting` 的区别: 本卡改变**结构**（切分/拼装），格式化改变**外观**（排版、进制）；要「把几个值排进一句话」走那条
- 与 `regex-construction` 的区别: 模式串与待匹配文本都是字符串，转义与拼接口径共用；固定分隔符切分不需要正则，分隔规则是「模式」时才走那条

## E — 可执行步骤 (Execution)

1. **定路线**
   - 完成标准: 判定是「字符↔字节」（编码问题）还是「一个字符串↔一组字符串」（切分/拼装）

2. **声明口径**
   - 完成标准: 编码路线写出目标编码与 errors（不写就是 UTF-8 + strict）；切分路线写出 sep（不写就是所有空白符）与 maxsplit；拼装路线确认分隔符写在点号左边
   - 判停条件: 说不出编码时按数据来源声明判定；仍判不出就显式试 UTF-8 并注明假设

3. **执行转换**
   - 完成标准: encode/decode 成对使用同一编码；split 与 join 成对出现在同一次数据流里

4. **校验**
   - 完成标准: 编码往返结果与原文一致；拼接结果的分隔符数量 = 元素数 - 1；受限切分的元素个数 ≤ maxsplit+1

- **输入契约**: 必需——待处理字符串、目标编码、分隔符与 maxsplit、元素列表。缺失时先问用户，不要替他默认编码或分隔符；数据含非法字符必须显式选 errors（默认 strict 会抛异常）。
- **输出契约**: 交付①路线判定②口径声明③调用写法④校验结论。完成标准是校验逐条通过，且未重建 OCR 丢失的转义符号表。

## B — 边界 (Boundary) ★

### 不要在以下情况使用这张卡
- 要按模式抽取字段（多种分隔符、变长空白、需要捕获）——走 `regex-construction`
- 要排版、位数、进制转换、百分比——走 `string-formatting`
- 要取字符串里的一段——走 `sequence-slicing`
- 转义字符的符号清单：该表在 OCR 中丢了符号列（unit_note / g02），本书未覆盖

### 作者在书中警告的失败模式
- errors 默认 strict（ce07）：「遇到非法字符就抛出异常」是默认行为，要容错必须显式改 errors
- maxsplit 数的是刀数不是块数（ce08）：不指定或为 -1 时分割次数没有限制，否则结果列表元素个数最多为 maxsplit+1；OCR 把 -1 识别成 `-l`，引文照抄未改
- split 的 sep 默认不是逗号（f12）：默认 None 表示所有空白字符，要按逗号切必须显式传分隔符

### 作者盲点与底本缺口
- 转义字符表在 OCR 中损毁（符号列丢失），本书该处不可复原：本卡只保留规则句「使用反斜杠对一些特殊字符进行转义」，不重建符号表（unit_note、g02）。
- 证据基础 6 条候选；g02 属第 2 章，作为「字符串里的转义」的单列 reference。
- join 对非字符串元素的处理、split 后空字段的去留——本书未覆盖。

### 容易混淆的邻近方法论
- `string-formatting`: 都产出字符串；含占位符与格式字符的走那条，纯分隔符连接的走本卡。
