# 飞船操控与子弹编组（第12章下半）

## R — 原文 (Reading)

> 当前，子弹抵达屏幕顶端后消失，这仅仅是因为Pygame无法在屏幕外面绘制它们。这些子弹实际上依然存在，它们的y坐标为负数，且越来越小。这是个问题，因为它们将继续消耗内存和处理能力。
>
> — 第12章 12.8.5 删除已消失的子弹（L16482-L16482）

## I — 方法论骨架 (Interpretation)

这个能力解决三件事：**让飞船按住方向键持续移动、松开即停**，**把移动限制在屏幕内**，以及**把子弹做成可批量管理、可回收、有上限的编组**。三者共用一个口径——事件只记录意图，位置只在逐帧更新里变化。

持续移动靠**标志位**：KEYDOWN 把 moving_right / moving_left 置 True，KEYUP 复位为 False；真正改坐标的是 Ship.update()。主循环顺序固定为「检测事件 → 更新位置 → 刷新屏幕」，保证画出来的是更新后的位置。

两个方向可能同时成立，所以 update() 里的左右判定用**两个独立 if**：同时按住时先加后减、位置保持不变；事件分发处用 elif 反而安全——每个按键事件只与一个键关联。这是本卡的第一个高频坑判据（对照失败模式 ce107）。

改坐标之前先做**边界比较**：向右要求 rect.right < screen_rect.right，向左要求 rect.left > 0，飞船触及边缘即停住。速度用小数因子（像素/帧）表达，但 rect 的 centerx 等属性只存整数——把精确位置放进可存小数的属性（self.center = float(self.rect.centerx)），逐帧累加后再回写 rect。

子弹走 **Sprite + 编组**：Bullet 继承 Sprite，用 pygame.Rect(0, 0, 宽, 高) 从空白建矩形，centerx 对齐飞船、top 对齐飞船顶部；bullets = Group() 在主循环外只创建一次，bullets.update() 批量推进，绘制时遍历编组逐个画。

两条硬判据给收尾：**删除编组元素必须遍历副本**（bullets.copy()）——「看不见」不等于「已销毁」，y 为负的出屏子弹仍占内存与算力；**调试用 print 核实后立即删除**——它留在每帧路径里比绘图更费时。

## A1 — 书中的应用 (Past Application)

### 案例 1: 让飞船持续移动（KEYDOWN/KEYUP + moving_right）
- **类型**: 原书例题（可运行示范）（第12章 12.6.1-12.6.2）
- **问题**: 每按一次键只移动 1 像素，按住不放无法持续移动。
- **方法论的使用**: 先写「KEYDOWN 时直接改位置」的第一版；随后改为标志位方案——Ship 增加属性 self.moving_right = False 与方法 update()，check_events 在 KEYDOWN 置 True、在 KEYUP 置 False，主循环在事件检测之后、屏幕更新之前调用 ship.update()。
- **结论**: 每次按键都被注册为一个 KEYDOWN 事件；把「意图记录」与「位置更新」分离，更新顺序保证飞船按新位置绘制。
- **结果**: 运行并按住右箭头键，飞船将不断地向右移动，直到松开为止（L15806）。

### 案例 2: 左右同时按键与两个独立 if 的取舍
- **类型**: 原书例题（可运行示范）（第12章 12.6.3）
- **问题**: 增加向左移动后，两个方向可能同时成立，分支写法直接影响手感。
- **方法论的使用**: Ship 增加 self.moving_left；update() 中向左/向右写成两个独立 if 而不是 elif——同时按住时先增大 centerx 再降低它，位置保持不变；事件分发处保留 elif，因为每个事件只与一个键相关联。
- **结论**: if 还是 elif 取决于「两个条件是否可能同时为真」；用 elif 会让右箭头键始终处于优先地位。
- **结果**: 能够不断地左右移动飞船；同时按左右箭头键时飞船纹丝不动（L15892）。

### 案例 3: 回收出屏子弹并限制同屏数量
- **类型**: 原书例题（可运行示范）（第12章 12.8.5-12.8.6）
- **问题**: 子弹在屏幕顶端「消失」只是绘制不到，y 坐标为负仍留在编组里消耗内存与算力；同时希望限制同屏子弹数，鼓励有目标地射击。
- **方法论的使用**: 主循环在 bullets.update() 之后遍历 bullets.copy()，对 bullet.rect.bottom <= 0 的子弹调用 bullets.remove()；先用 print(len(bullets)) 观察子弹数随消失逐渐降为零，确认无误后删掉这条 print；发射前判断 len(bullets) < ai_settings.bullets_allowed（书中取 3）。
- **结论**: 编组不会自动回收出屏元素；遍历中删除必须针对副本；调试输出留在每帧路径会大大拖慢游戏。
- **结果**: 发射子弹后，终端中的子弹数随子弹一颗颗消失逐渐降为零（L16524）；屏幕上最多只能有 3 颗子弹（L16598）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想让角色「按住方向键持续移动、松手即停」，现在的写法一次按键只动一格。
2. 角色移出屏幕边界后消失/回不来，或同时按下相反方向键时行为不符合预期。
3. 子弹、道具这类数量多的同类元素要批量更新、批量绘制，还要能回收和限数。
4. 游戏越玩越卡，怀疑是逐帧路径里反复创建对象或留下了调试输出。

### 语言信号

- 「按住方向键它只动一下，怎么让它一直走」
- 「同时按左右键的时候它为什么只往一边走」
- 「飞船跑出屏幕就找不到了」
- 「子弹打出去就不见了，可游戏越玩越卡」
- 英文: "hold the arrow key to keep moving", "it keeps spawning but never disappears", "the game slows down after a while"

### 与相邻能力的区分

- 与 `pygame-project-setup` 的区别: 那张卡搭的是最小骨架（事件循环、Settings、刷新屏幕）；本卡在骨架上做「操控与射击」的行为层——按键状态、边界限制、子弹编组。
- 与 `pygame-aliens-and-collisions` 的区别: 本卡只管我方元素（飞船与子弹）的运动与回收；那张卡处理敌方群体的生成、整群移动与碰撞击杀。

## E — 可执行步骤 (Execution)

1. **建立按键状态与位移方法**
   - 完成标准: 按住方向键期间飞船逐帧持续移动、松开立即停止；标志位只记录意图，位置调整集中在 Ship.update()；主循环顺序为「检测事件 → 更新位置 → 刷新屏幕」。
   - 判停条件: 若需求是单次按下响应一次（菜单类），不要用标志位，直接在事件分支里处理。
2. **判定双方向分支写法并加边界限制**
   - 完成标准: update() 中左右判定为两个独立 if（不得用 elif）；同时按住左右键时位置保持不变；修改坐标前检查 self.rect.right < self.screen_rect.right 与 self.rect.left > 0，飞船触及边缘后停止移动、不出屏。
   - 判停条件: 需要斜坡加速、多方向复合运动时超出本卡口径，先按向量/加速度模型另立方案。
3. **速度参数化与浮点位置**
   - 完成标准: 速度因子集中存于设置对象（书中 ship_speed_factor = 1.5）；位置用可存小数的属性（self.center = float(self.rect.centerx)）逐帧累加，再回写 rect.centerx；不会因 rect 取整而丢失移动量。
   - 输入契约: 速度因子单位为「像素/帧」；输出契约: rect.centerx 为用于绘制的整数坐标。
4. **建立子弹实体与编组**
   - 完成标准: Bullet 继承 Sprite、用 pygame.Rect(0, 0, 宽, 高) 从空白建矩形（centerx 对齐飞船、top 对齐飞船顶部）；参数集中在设置对象（速度 1、宽 3、高 15、深灰 (60, 60, 60)）；bullets = Group() 在主循环外只创建一次；bullets.update() 批量推进；绘制时遍历编组逐个画，并让子弹位于飞船/外星人之后（先画子弹，再画飞船）。
   - 判停条件: 需要「击中多个目标仍存活」的穿行弹药时，碰撞实参口径要改（见外星人单元的 groupcollide 用法），本卡不覆盖。
5. **回收出屏子弹并限制数量**
   - 完成标准: 删除只遍历 bullets.copy()，命中 bullet.rect.bottom <= 0 才 remove；编组长度随子弹出屏回落而不是只增；发射前判断 len(bullets) < bullets_allowed（书中 3，可按玩法另定）；验证用 print(len(bullets)) 确认后必须删除，每帧路径无遗留输出。
6. **把成块逻辑搬进函数**
   - 完成标准: 子弹更新与删除进入 update_bullets()、发射进入 fire_bullet()（移入 game_functions）；主循环只保留「检查输入 → 更新飞船 → 更新子弹 → 刷新屏幕」的函数名级调用，行为与搬移前一致。

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 只需一次性按键响应（菜单选择、开/关切换）——标志位 + update() 是为「按住持续生效」准备的，单次响应用事件分支即可。
- 引擎/框架用固定时间步或 delta time 推进时，速度因子与 update() 口径需要另行换算，不能照搬像素/帧模型。
- 元素数量很少、生命周期极短的场景，编组与回收机制的复杂度可能不划算（收益在批量管理与长时间运行）。

### 作者在书中警告的失败模式

- ce107: 左右移动的 update() 用 elif 处理反向标志——右箭头键将始终处于优先地位，同时按键时飞船响应不跟随意图；必须写成两个独立 if。
- ce111: 在 for 循环中直接删除原编组/列表条目——会跳过元素或提前结束循环，表现为「删不干净」的随机漏网；必须遍历副本（bullets.copy()）。
- ce112: 验证用 print 忘记删除——写终端比绘制图形更耗时，留在每帧路径里游戏速度将大大降低。
- ce106: 位置更新只做加法、没有边界检查——飞船移到屏幕外面消失得无影无踪，玩家只能重启。

### 作者的盲点 / 时代局限

- 速度因子的「最佳值」没有客观标准，书中只给「依系统而定」（第13章的反例 ce120 继续展开「工作量增加让子弹变慢」）；也缺少按时间（delta time）推进的替代方案。
- 遍历时删除的机制解释（迭代位置与元素错位）书中未给，只给「不应在 for 循环中删除条目」的规则；本卡同样只保留规则口径。
- 全书是 2016 年技术栈快照（Python 3.5 / Pygame 1.9.2a0，Pygame 从 Bitbucket 源安装、Windows 另有 .whl 安装包），安装与依赖步骤须按现环境替换（2016 年快照）。
- 转档稿中多处代码与正文粘连、缩进丢失（如 L16068、L16438-L16444 一带），照代码块抄写时需自行补回缩进。
