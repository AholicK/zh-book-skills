## I — 方法论骨架 (Interpretation)

这套方法处理程序与「外部世界」之间的三件事：文件读写、坏输入兜底、以及代码能跑之后的结构改进。

读取的固定动作是「打开 → 读出 → 自动关闭」：`with open(...) as file_object:` 把关闭责任交给 Python，不要在块外继续使用文件对象；读法三选一——要整段字符串用 `read()`，要逐行处理用 `for line in file_object`（配 `rstrip()` 消掉多余空行），要留到块外继续用就先 `readlines()` 存成列表。文件里的文本一律被解读为字符串，数字要参与计算必须先 `int()`/`float()` 转换。

写入先选模式：`'w'` 在返回文件对象之前就会清空既有内容——只想追加就必须用 `'a'`；`write()` 不会替你补换行符，数值要先 `str()`。要跨程序保留数据，用 `json.dump()` / `json.load()` 往返。

异常把「意外」和「正常」分开：`try` 只装可能引发目标异常的代码，`except` 指定类型并写善后，依赖 `try` 成功才运行的代码放 `else`。处理 `FileNotFoundError` 时，`try` 必须放在包含 `open()` 的那一行之前；捕获之后报告还是沉默是可调决策——用户不知情就 `pass`，用户要知道原因就报告。

最后一步是重构：代码能跑之后，把不同职责拆进各自函数，每个函数只做一件事；「要么返回预期的值，要么返回 `None`」让返回值可以直接参与判断。

## A1 — 书中的应用 (Past Application)

### 案例 1: 除零、缺文件与多文件批处理
- **类型**: 原书例题（可运行示范）（第10章 10.3）
- **问题**: 除法计算器遇到除数为 0 直接崩溃；批量分析多本书时，一个文件缺失就让程序停下，后面的文件不再处理。
- **方法论的使用**: 先用 print(5/0) 看到 ZeroDivisionError 的 traceback，再用 try/except 打印友好消息；把 `answer = int(first_number) / int(second_number)` 放进 try、把结果打印放进 else；alice.py 把含 open() 的行包进 try、except FileNotFoundError 给出提示；word_count.py 把逻辑封装为 count_words(filename)，对多本书循环调用，缺 siddhartha.txt 不中断其余文件。
- **结论**: 未处理的异常=程序停止+traceback；处理之后程序继续运行、只给友好消息；「报告还是 pass」按用户是否需要知情决定。
- **结果**: 书中给出的输出：You can't divide by zero!、You can't divide by 0!、The file alice.txt has about 29461 words.；多文件版另含 Sorry, the file siddhartha.txt does not exist. 与其余书的词数。

### 案例 2: remember_me.py——json 往返与三轮重构
- **类型**: 原书例题（可运行示范）（第10章 10.4）
- **问题**: 用户不想每次运行都重新输入名字；程序跑通后，单个函数同时负责问候、取数和存数。
- **方法论的使用**: 先用 number_writer.py / number_reader.py 验证 json.dump() 与 json.load() 的往返；remember_me.py 以 try 打开 username.json 并 load → except FileNotFoundError 提示输入并 dump 保存 → else 欢迎老用户；再做重构——先整段放进 greet_user()，再拆出 get_stored_username()（缺文件返回 None）与 get_new_username()。
- **结论**: 每个函数只执行单一而清晰的任务；「要么返回预期的值，要么返回 None」让返回值可直接用于判断。
- **结果**: 书中给出的输出：[2, 3, 5, 7, 11, 13]（读写两端一致）；We'll remember you when you come back, Eric! 或 Welcome back, Eric!。

### 案例 3: 写入 programming.txt 的三种动作
- **类型**: 原书例题（可运行示范）（第10章 10.2）
- **问题**: 把内容写进文件、写多行、再往文件末尾追加内容。
- **方法论的使用**: open(filename, 'w') 写入内容（文件不存在自动创建）；两次 write() 不加换行会挤成一行——补上 "\n" 后各占一行；改用 'a' 模式把新内容加到末尾，原有内容保留。
- **结论**: 写入用 'w' 会先清空既有文件（覆盖即销毁旧数据），追加必须用 'a'；write() 不替你补换行符。
- **结果**: 书中给出的输出：programming.txt 从一行内容、到两行、再到追加后共四行的文件内容。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想把程序运行结果保存下来、下次运行再读回来（用户名、记分、清单）
2. 读文件时遇到 FileNotFoundError，不确定文件该放哪、路径该怎么写
3. 想给已有文件补充内容，又怕把原来的数据搞丢
4. 程序一碰到坏输入或缺失文件就崩溃，希望它提示之后继续跑
5. 代码能跑但太长太乱，想把「读、算、存」拆开

### 语言信号

- 「文件明明存在，程序却说找不到」
- 「怎么把数据存到文件里、下次再读回来」
- 「写入会不会把原来的内容清空？」
- 「一运行就报 traceback，怎么让它别崩」
- 英文: "FileNotFoundError: [Errno 2] No such file or directory", "how do I append to a file without overwriting it", "save data to a json file and load it back"

### 与相邻能力的区分

- 与 `functions-and-modules` 的区别: 那条讲函数与模块的写法（实参、返回值、导入）；本卡的重构是「代码已经能跑之后」按单一职责拆分，并落在文件与异常场景；
- 与 `unit-testing` 的区别: 测试回答「改动有没有破坏行为」；本卡回答「结构怎么拆、文件怎么读写、出错怎么兜」——先有单一职责的函数，测试才有的放矢；
- 与 `data-parsing-and-cleaning` 的区别: 那条处理外部数据文件的内容质量（表头、缺测、类型清洗）；本卡只管读写机制与异常兜底，不替数据质量把关。

## E — 可执行步骤 (Execution)

1. **定路径、定读法**
   - 完成标准: 数据文件与程序同目录（或子目录）；引用子目录文件用相对路径（Windows 用反斜杠）、必要时用绝对路径且存进变量；读法按需求三选一（read / 逐行 / readlines），数值已 int()/float() 转换，输出无多余空行
   - 判停条件: 报「找不到文件」时先按三级选择核对路径，再怀疑文件名拼写
2. **定写入模式与持久化方式**
   - 完成标准: 追加需求使用 'a'（绝不用 'w' 打开既有数据文件）；多行写入自带 \n；数值已 str() 转换；跨次运行的数据用 json.dump() / json.load() 往返，读回与写入一致（.json 扩展名）
   - 输出契约: 目标文件内容符合预期，原有数据未被清空
3. **为外部依赖布置异常**
   - 完成标准: try 只包可能引发目标异常的代码（含 open() 的那一行必须在 try 内）；except 指定类型并给出用户能懂的消息；依赖成功才运行的代码在 else；运行出错时用户看不到裸 traceback
   - 判停条件: 「报告还是 pass」按用户视角决定——知道有哪些文件/数据就报告原因，只看结果可以不打扰（pass 是明确的沉默决策，不是偷懒）
4. **走一遍失败路径**
   - 完成标准: 人为制造两类已知失败（文件缺失、除零或等价坏输入）后，程序按设计继续运行、输出只有友好提示；其余待处理的数据没有被漏掉
5. **重构收尾**
   - 完成标准: 每个函数能用一句话概括唯一职责；拆分后两条分支（首次运行 / 再次运行）都能直达预期输出

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 多人或多进程同时写同一文件——本卡口径是单程序顺序读写，没有并发控制手段；
- 需要结构化查询或事务性保证时——文本文件与 json 只是「存取」，此类需求应换用数据库；
- 文件巨大且需要随机访问某一段时——原书只有整体读取与逐行读取两种模式，未涉及分段定位。

### 作者在书中警告的失败模式

- ce72：以写入（'w'）模式打开已存在的文件时，Python 会在返回文件对象前清空它——本意「更新」，打开动作本身已经销毁旧数据；
- ce70：逐行读取时每行末尾有两个换行符叠加（文件自带一个、print 再加一个），输出凭空多出空行；
- ce76：把一大批代码塞进 try——不该被吞掉的错误也被吞掉，程序「不报错」但结果缺失；只有可能引发异常的代码才进 try，依赖成功的代码放 else；
- ce77：在 except 里写 pass 让失败一声不吭——没有 traceback 也没有任何输出，事后无法回答「这次运行漏掉了什么」。

### 作者的盲点 / 时代局限

- 2016 年快照，按现环境替换：异常类型只示范了 ZeroDivisionError 与 FileNotFoundError 两类，ValueError 等数据错误、文件编码、pathlib 与新字符串格式都要按现环境补充；
- 原书未讨论并发、原子写入与编码问题；'r+' 模式只有命名、没有使用示例；
- 转档缺陷：代码清单在转档中有缩进损失，L13338 处示例首行为「mport json」[原文如此]，照抄时须自行核对修正，不要误判为环境问题。

### 容易混淆的邻近方法论

- `functions-and-modules`: 也讲把代码放进函数与模块，但那是在「写函数」时的组织规范；本卡的重构口径是「代码已经能跑之后」按单一职责拆分（10.4.3）；
- `unit-testing`: 测试负责验证行为是否被破坏；本卡负责把函数拆到职责单一、行为可核对，两者配合使用；
- `data-parsing-and-cleaning`: 处理外部数据文件时先打印核对再清洗；本卡只负责读写机制与异常兜底。
