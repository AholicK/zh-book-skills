# 用户账户与数据归属（第19章）

## R — 原文 (Reading)

> 现在，需要将数据关联到提交它们的用户。我们只需将最高层的数据关联到用户，这样更低层的数据将自动关联到用户。例如，在项目“学习笔记”中，应用程序的最高层数据是主题，而所有条目都与特定主题相关联。只要每个主题都归属于特定用户，我们就能确定数据库中每个条目的所有者。
>
> — 第19章 19.3.2 将数据关联到用户（L27588-L27588）

## I — 方法论骨架 (Interpretation)

这一条把「单人能用的网站」升级成「多人各用各的网站」，由三组机制拼成，顺序不能颠倒：

- **表单（数据入口）**: 页面一律用 ModelForm 由模型自动生成；视图固定分两支——非 POST 时返回空表单，POST 时用提交数据构造表单、`is_valid()` 通过后保存并重定向（重定向防止刷新或后退时重复提交）。表单里装不下的关联字段，用 `form.save(commit=False)` 先拿到对象、补上值、再 `save()`；编辑既有记录靠 `instance=对象` 预填，并在按钮文案上点明「保存修改而非新建」。
- **账户（身份入口）**: 单独建一个应用承载用户功能（进 `INSTALLED_APPS` + 项目级路由 include 命名空间 + 应用内路由）；登录直接复用现成视图，用字典把模板位置交给它，并用隐藏字段 `next` 指定登录成功后回哪；注销是「调用后重定向」的三行函数；注册保存用户后走两步自动登录（先验证、再建立会话）。
- **归属（数据出口）**: 只给最高层数据挂所有者外键，下层数据顺着外键自然确定归属；三个动作缺一不可——页面入口加登录限制并配置好重定向地址、列表查询按当前用户过滤、详情/编辑页取到对象后核对归属，不匹配就返回「找不到」。
- 判据: 链接被隐藏不等于被保护——直接输入 URL 也必须被拦住；「查看、输入、修改」三条路径要各自被覆盖。

## A1 — 书中的应用 (Past Application)

### 案例 1: 添加新主题的表单页
- **类型**: 原书例题（可运行示范）（第19章 19.1.1 添加新主题）
- **问题**: 需要让用户在页面上录入主题并入库，同时挡住格式不合法的输入
- **方法论的使用**: `forms.py` 里用 `TopicForm(forms.ModelForm)`（`Meta` 指定 `model = Topic` 与 `fields = ['text']`）；视图 `new_topic()` 分两支——非 POST 返回 `TopicForm()`，POST 用 `TopicForm(request.POST)` 并在 `is_valid()` 后 `form.save()`，随即 `HttpResponseRedirect(reverse('learning_logs:topics'))`；模板用 `<form ... method='post'>` + `{% csrf_token %}` + `{{ form.as_p }}` 加自己写的提交按钮
- **结论**: 表单页 = GET/POST 双分支 + 自动验证 + 保存后重定向；`is_valid()` 按模型定义核对必填与字段类型（如 text 少于 200 字符），省去大量手工校验
- **结果**: 书中给出的结果：图19-1 表单可用，提交后主题出现在 topics 列表

### 案例 2: 给主题加所有者并限制页面访问
- **类型**: 原书例题（可运行示范）（第19章 19.3.1-19.3.2）
- **问题**: 要先确定「哪些页面不设防」，再把既有数据迁移成「有主」的状态
- **方法论的使用**: 为 `topics()` 等视图加 `@login_required`，在 `settings.py` 末尾设 `LOGIN_URL = '/users/login/'`；决定不限制主页、注册、注销，其余全部限制；模型加 `owner = models.ForeignKey(User)`；迁移前用 shell 查好用户 ID，迁移命令提示「添加了不可为空且无默认值的字段」时选择「现在提供一次性默认值」并输入该 ID
- **结论**: 装饰器只管「拒绝并转向」，转向地址由配置项提供；含既有数据的迁移可用一次性默认值完成，不必清库
- **结果**: 书中给出的结果：未登录访问受限页面被重定向到登录页；迁移输出 `Applying learning_logs.0003_topic_owner... OK`；既有主题归属 ll_admin

### 案例 3: 只让用户看到自己的数据
- **类型**: 原书例题（可运行示范）（第19章 19.3.3-19.3.4）
- **问题**: 不论以哪个用户登录都能看到全部主题；详情页还能靠改 URL 看到别人的条目
- **方法论的使用**: 列表页改成 `Topic.objects.filter(owner=request.user).order_by('date_added')`，模板无需改动；详情页取到对象后先核对归属，`if topic.owner != request.user: raise Http404`
- **结论**: 列表页的过滤只影响「显示哪些」，不构成访问控制；详情页的关键是「取到数据之后核对归属」
- **结果**: 书中给出的结果：以另一用户登录时 topics 页不列出主题；访问他人主题显示 Page Not Found

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要做一个多用户的应用，担心别人能看到、改到自己的数据
2. 表单一点提交就报 403 或者没反应，不知道少写了什么
3. 提交成功后刷新页面，浏览器提示「重新提交表单」，列表里出现重复记录
4. 给模型加 owner 字段后，迁移命令停下来要你输入默认值
5. 编辑页面提交后原记录没变，反而多出一条新记录

## E — 可执行步骤 (Execution)

1. **接入用户应用**
   - 完成标准: 新应用的目录结构与既有应用一致；应用名已进 `INSTALLED_APPS`；项目级路由用 include + 命名空间把它挂上；应用内 `urls.py` 定义了注册、登录、注销等页面模式
   - 输入契约: 一个已跑通的 Django 项目 + 要提供的入口清单（注册/登录/注销）
   - 输出契约: 可被路由到的新应用 + 一份「哪些页面不设防」的名单

2. **写表单页（GET/POST 双分支）**
   - 完成标准: 非 POST 分支返回空表单；POST 分支构造带数据的表单，校验通过后保存并重定向到列表页；模板含 `{% csrf_token %}`、`{{ form.as_p }}` 与自己写的提交按钮
   - 判停条件: 提交后出现 403，先回来核对 csrf_token 与请求方法，再往下走

3. **给表单保存补上关联字段**
   - 完成标准: 凡是「表单里没有、数据库里不可为空」的字段，都在最终 `save()` 之前显式赋值（`new_entry = form.save(commit=False)` → 补字段 → `save()`）；编辑页 GET 用 `instance=` 预填、POST 同时传 `instance=` 与提交数据
   - 判停条件: 保存时报完整性/关联字段错误，回来检查这一步的外键赋值是否遗漏

4. **配好账户链路**
   - 完成标准: 登录页用现成视图 + 字典指定模板，表单带隐藏字段 `next`；注销调用后重定向；注册在保存后进行「验证 → 建立会话」两步自动登录；页眉按登录状态切换显示注册/登录或问候/注销

5. **上三道闸并逐条复验**
   - 完成标准: ① 受保护的视图都加了登录限制，且重定向地址已在设置文件里配置；② 列表查询按当前用户过滤；③ 详情与编辑页取到对象后核对归属，不匹配返回「找不到」；④ 新建路径在保存前补上所有者。复验: 用第二个账号直接输入他人记录的地址，应得到「找不到」而不是任何数据

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 单人使用、不含他人数据的工具站——账户系统与归属字段带来的迁移与维护成本收不回来。
- 需要邮件确认、找回密码、双因素、限流等真实身份能力的场合——书里的注册系统刻意从简，不要直接照搬上线。
- 项目已采用成熟认证方案时——本卡的口径是「自己动手搭最小可用系统」。

### 作者在书中警告的失败模式

- **ce181（只挡列表不挡详情）**: 只做了按所有者过滤列表，详情页仍按 URL 里的 id 直取——任何已登录用户把 id 换成别人的，就能看到他人全部条目；过滤只影响「显示哪些」，不是访问控制。
- **ce182（新数据缺归属字段）**: 模型加了不可为空的外键后，旧的保存流程没有补该字段——用户提交表单时直接抛数据库完整性错误（user_id 不能为 NULL）。
- **ce179（给既有数据加不可为空外键）**: 迁移会被拦下，必须为既有数据行提供一次性默认值（要事先查好用户 ID），否则迁移无法生成。
- **ce171（表单漏掉 csrf_token）**: 页面能打开、能填写，一点提交就被拒——POST 表单默认有跨站请求伪造防护，模板里不携带令牌，服务端就不处理。

### 作者的盲点 / 时代局限

- **2016 年快照，按现环境替换**: 本卡基于 Django 1.8.4 的 `url()` 路由与当时的默认认证视图写法；版本升级后相关写法与默认值都有变化，请按现环境核对。
- 注册系统刻意从简: 作者自己注明没有邮件确认、「允许用户创建任意数量的账户」，垃圾账户会更多（ce177）——练习可用，上线必须补身份确认。
- 越权的复现与复验靠读者手工开两个账号验证，书中没有自动化回归测试；「哪些页面不设防」的名单也靠人工维护。
- 图 19-1～19-5 的内容在文本转档中丢失，只剩图注；页面外观与流程截图无法按书核对。

### 容易混淆的邻近方法论

- `django-project-basics`: 本卡的前置——模型、迁移与页面三处写法都在那一条；本卡只在「保存要补外键 / 补所有者」时回指它。
- `django-styling-and-deploy`: 本卡收尾的项目就是它的起点；部署前必须确认三道闸都通过，尤其别把调试开关带上线。
