# 字典与嵌套建模（第6章）

## R — 原文 (Reading)

> 字典可用于以各种方式存储信息，因此有多种遍历字典的方式：可遍历字典的所有键—值对、键或值。
>
> — 第6章 6.3 遍历字典（L6783-L6783）

## I — 方法论骨架 (Interpretation)

字典把数据组织成「键 → 值」的关联：用键取值，增/改用 d[键] = 值 一句完成，删除用 del d[键]（键—值对就此消失）。值可以是数字、字符串、列表乃至另一个字典——这是后面一切嵌套的底座。

与列表最大的不同是顺序语义：字典不做顺序承诺，添加顺序与返回顺序都可能不一致，一切按「关联关系」理解；确实需要顺序时，在遍历处显式排序（sorted() 包一层）。据此，遍历选型按需索取：要键和值用 items()，只要键用 keys()（遍历字典默认就是遍历键，显式写出更易读），要顺序用 sorted()，只要值用 values()，值可能重复用 set(values()) 去重。

数据来自用户或需要自动生成时，从空字典 {} 起步、分行添加是常规做法；多行字典有固定书写格式：左花括号后回车、缩进四个空格、行尾留逗号、右花括号与键对齐。

嵌套是把两类容器互相装进去，三种形态对应三种建模需求：一批同类对象各带多项信息 → 字典列表；一个对象、某属性有多个值 → 字典存列表；一批对象、每对象又是一组信息 → 字典存字典。通用处理代码的前提是内层结构同构；层级不应太多——远比示例复杂时，多半存在更简单的方案。

也可以用字典的值驱动行为：把 speed 之类的参数存进字典，改一个值就改变整套行为，无需改逻辑。

## A1 — 书中的应用 (Past Application)

### 案例 1: alien_0 的创建、取值与添加
- **类型**: 原书例题（可运行示范）（第6章 6.1–6.2.3）
- **问题**: 建立一个外星人档案：读取颜色与点数，并在之后补上位置信息。
- **方法论的使用**: 花括号定义 {'color': 'green', 'points': 5}；用 alien_0['color'] 按键取值并拼消息；用 alien_0['x_position'] = 0 逐项添加键—值对；并示范空字典起步（alien_0 = {} 再分行添加）。
- **结论**: 键—值对排列顺序与添加顺序不同（示例中 y_position 排在 x_position 之前）；存储用户数据或自动生成大量键—值对时，先定义空字典是常规做法。
- **结果**: 输出 green 5、You just earned 5 points! 与 {'color': 'green', 'points': 5, 'y_position': 25, 'x_position': 0}；空字典起步版的最终输出未说明。

### 案例 2: 从三个外星人到 range() 生成 30 个（字典列表）
- **类型**: 原书例题（可运行示范）（第6章 6.4.1）
- **问题**: 需要管理一批同类对象，并且批量生成、筛选修改。
- **方法论的使用**: 把多个外星人字典放进列表 aliens；用 for alien_number in range(30) 循环生成同构字典并 append；用切片（aliens[:5]、aliens[0:3]）抽查，配合 if 只把绿色外星人改为黄色。
- **结论**: 多个同类对象、每个对象多项信息用字典列表承载；批量修改用切片定位 + if 判断。
- **结果**: 前五个 {'speed': 'slow', 'color': 'green', 'points': 5}，并打印 Total number of aliens: 30；修改后前三个变为 {'speed': 'medium', 'color': 'yellow', 'points': 10}。

### 案例 3: many_users.py 字典中存储字典
- **类型**: 原书例题（可运行示范）（第6章 6.4.3）
- **问题**: 多个用户、每人一组信息（名、姓、居住地），需要统一遍历输出。
- **方法论的使用**: 外层 users 字典的值为信息字典（内层均含 first/last/location 三键、保持同构）；for username, user_info in users.items() 遍历外层，再用 user_info['first'] 等访问内层。
- **结论**: 内层字典结构相同使统一处理成为可能；作者同时提醒列表与字典的嵌套层级不应太多。
- **结果**: 输出 Username: aeinstein / Full name: Albert Einstein / Location: Princeton，以及 mcurie 对应的三行记录。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 给「实体 + 多个属性」建模（一件商品多字段、一个用户多信息），不确定用列表还是字典
2. 遍历字典时发现输出顺序和录入顺序不一致
3. 想把一个键关联到多个值（一份订单多个配料），数据越写越乱
4. 要改一个值或删一个键—值对，担心波及别处；或想从空字典起步逐项录入
5. 嵌套到了两三层，代码越来越难读，想知道结构是否合理

### 语言信号

- 「字典的键怎么取值、怎么加新条目？」
- 「遍历出来的顺序和我添加的顺序不一样？」
- 「一个键对应多个值，该怎么存？」
- 「这几个字典套来套去，我自己都看晕了」
- 英文: "how do I iterate over a dict", "the order isn't what I expected", "too many nested levels"

### 与相邻能力的区分

- 与 `list-operations` 的区别: 那条处理有序序列的取值、增删与切片；本卡用列表承载「一个键对多值」并负责字典侧的读写遍历——列表自身的操作回到那条。
- 与 `data-parsing-and-cleaning` 的区别: 那条把外部数据（JSON 等）收拾干净、处理缺失；本卡先给出字典结构与遍历口径，数据落成字典之后再去那边清洗。

## E — 可执行步骤 (Execution)

1. **定形**
   - 完成标准: 判定属于三形态中的哪一类（字典列表 / 字典存列表 / 字典存字典），写出一层结构草图（如 [{'color': ...}, ...] 或 {name: {'first': ...}}）
   - 判停条件: 若嵌套将超过书中示例规模（三层），先停下评估拆分或更简单的方案
2. **建骨架**
   - 完成标准: 多行字典按格式书写——左花括号后回车、缩进四个空格、最后一行右花括号与键对齐、行尾逗号保留；数据来自用户或自动生成时改为空字典起步逐行添加
3. **增改删**
   - 完成标准: 新增与修改各演示一次 d[键] = 值；删除用 del d[键]，执行前声明「删除的键—值对永远消失」，并确认其后没有读取该键的代码路径
4. **遍历选型**
   - 完成标准: 五种写法各给一段骨架并注明适用——items()（键和值，变量用描述性名）、keys()（只要键）、sorted()（要顺序）、values()（只要值）、set(values())（去重）；需要固定顺序的输出确实经过排序，去重输出无重复项
   - 输出契约: 每段遍历的循环变量与取值表达式一一对应（如 for k, v in d.items()）
5. **嵌套访问与结构体检**
   - 完成标准: 同一段通用遍历能处理全部对象（内层键一致）；修改内层值先用切片/键定位再改；同层键不一致处要么补齐、要么注明分支代价；层级不超过示例规模
6. **收尾核对**
   - 完成标准: 三项结论齐备——①不依赖字典顺序（需要顺序处已显式排序）；②删除的影响范围已确认；③set 仅用于去重、未扩展集合运算；改动后重跑遍历，输出与预期一致

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 数据本身强调顺序（名次、步骤序列）——那是列表的语义，用列表承载
- 只需要存「一个值」——普通变量即可，不要为单值建字典
- 外部数据还是原始 JSON、需要核对字段与处理缺失时——先转 `data-parsing-and-cleaning`

### 作者在书中警告的失败模式

- ce39（遍历顺序不可预测）：键—值对的返回顺序与存储顺序不同；按「添加顺序」写展示逻辑、日志或断言，在不同运行中表现不一致——需要顺序必须显式排序
- ce47（del 彻底删除）：删除的键—值对永远消失；在仍需读取该键的路径之前就 del，会造成真实的数据丢失
- ce40（values() 不剔除重复）：提取所有值而不考虑重复，被调查者多时列表含大量重复项，「有哪些」「共几类」被重复污染，须用 set() 去重
- ce41 与 ce48（嵌套结构设计）：嵌套层级比示例多得多时多半存在更简单方案，访问代码出现三重以上括号连写就是信号；同一层级字典键各不相同，也会让通用遍历写不出来、循环体内被迫堆分支

### 作者的盲点 / 时代局限

- 2016 年快照：「获取字典元素的顺序不可预测」是成书时（2015–2016）技术栈下的口径；现代 Python 实现的保序行为与原书表述存在差异，原书未讨论——引用顺序口径时须注明版本前提，并按现环境验证
- set 仅按「对列表调用 set() 去重」引入，集合运算等超出原书范围，不要扩讲成完整的集合数据结构
- 嵌套只给到三层示例，更深的层级仅有一句「不应太多」的提醒，没有判定细则
- 本电子文本经转档后代码缩进与图注丢失、部分输出行成对粘连；照抄与回源核对时以可逐字核对的片段为准

### 容易混淆的邻近方法论

- `list-operations`: 同一个键要多值时用列表入字典；列表的取值、切片、复制等操作回到那条
- `data-parsing-and-cleaning`: 数据落成字典之后的遍历与嵌套建模用本卡；缺测处置与格式清洗用那条
