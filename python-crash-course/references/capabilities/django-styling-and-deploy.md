## I — 方法论骨架 (Interpretation)

这一条是「功能完成之后」的两段工作，目标都是把项目从「本机能跑」变成「能给别人看、给别人用」。

- **样式（先功能、后外观）**: 先确保功能正确运行是有意为之的顺序——能正确运行的应用程序才是有用的。接入方式三步走：安装样式应用、把它加进 `INSTALLED_APPS`、在设置文件末尾加它自己的配置；然后把 `base.html` 换成样式框架的骨架（导航栏 + 容器 + 页头块 + 内容块），其余页面照同一套路逐个改造。纪律只有一句: **只改影响外观的元素，在页面中包含信息的那部分代码一行不动**。
- **部署（把环境差异收进声明与条件块）**: 需要三份声明加一个条件块——依赖清单（逐个装包、冻结版本、把平台管理的数据库驱动补进清单）、运行时版本声明（单行、小写 python + 连字符 + 三段版本号）、启动契约（单行进程声明 + 用能服务静态文件的包装器启动应用），以及设置文件末尾「仅服务器生效」的条件块（数据库、HTTPS 代理头、允许的主机、静态资产）。静态文件目录必须放一个占位文件，否则空目录不会被推送。
- **版本控制是部署的前置**: 忽略清单只管三类——可再生的（本地环境目录）、编译产物（缓存目录）、本地数据库文件（推送它会覆盖线上库）；提交后必须看到工作目录干净，才说明「即将推送的内容被全部纳入」。
- **加固（上线前后各一步）**: 调试开关必须关掉（否则任何触发错误的人都能看到完整堆栈、配置片段与源码路径）；允许访问的主机只列自己的域名；给「找不到」与「服务器错误」各准备一页；取对象改用「取不到就按找不到处理」的快捷函数。
- 判据: 迭代循环固定为「本地改 → 加入 → 提交 → 推送 → 按需在线上重跑迁移 → 访问线上验证」；本地数据默认不复制到线上。

## A1 — 书中的应用 (Past Application)

### 案例 1: 把 Bootstrap 推广到各页面
- **类型**: 原书例题（可运行示范）（第20章 20.1.5-20.1.8）
- **问题**: 主页已经套上样式框架，登录页、表单页、列表页与详情页还是裸 HTML
- **方法论的使用**: 每页套同一套路——登录页与表单页顶部加载样式标签、表单加 `class="form"`、用样式库的表单标签取代 `{{ form.as_p }}`、按钮包进按钮标签并加 `class="btn btn-primary"`、删掉自写的 `{% if form.errors %}` 块（样式库自动管理表单错误）；列表页标题改用 `h3`；详情页把每个条目包成面板（标题区放日期与编辑链接、主体区放文本）
- **结论**: 模板套用流程可复制到任意页面；全程只改影响外观的元素，包含信息的取数代码没有改动
- **结果**: 书中给出的结果：图20-2 与图20-3；功能没有任何变化，但显得更专业

### 案例 2: 部署配置三件套与静态目录
- **类型**: 原书例题（可运行示范）（第20章 20.2.6-20.2.9）
- **问题**: 同一份代码要在本地开发环境与线上服务器两种环境里跑
- **方法论的使用**: 设置文件末尾用 `if os.getcwd() == '/app':` 包住只在服务器生效的配置（数据库、HTTPS 代理头、允许的主机、静态资产）；在 `manage.py` 旁建启动声明文件（单行，以 `web: gunicorn 项目名.wsgi --log-file -` 开头）；修改 `wsgi.py`，把应用对象包进负责静态文件的服务包装器；建静态文件目录并放入占位文件
- **结论**: 环境差异靠运行目录自动判断，同一份设置文件两处通用；启动声明是平台读的契约；空目录要靠占位文件才能进入仓库
- **结果**: 未说明（该节为配置步骤，运行效果在推送上线后才体现）

### 案例 3: 上线安全加固与自定义错误页
- **类型**: 原书例题（可运行示范）（第20章 20.2.15-20.2.20）
- **问题**: 带着调试开关上线会把内部信息暴露给攻击者；对象不存在时返回的是服务器错误
- **方法论的使用**: 在线上分支把允许的主机缩到自有域名、调试开关设为关；用一个未定义的 URL 扩展请求验证错误页不泄露信息（同样的请求在本地仍显示完整调试页）；在模板目录建「找不到」与「服务器错误」两页并让模板搜索路径指向它们；把按 id 取对象改成「取不到就按找不到处理」的快捷函数
- **结论**: 错误页的详略是开发与线上两个环境的取舍；「对象不存在」应映射为 404 而不是 500
- **结果**: 书中给出的结果：线上错误页不泄露信息（本地仍显示完整调试页）；404 页面与网站风格一致

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 功能都跑通了，页面还是裸 HTML，想套一个现成的样式框架
2. 想把本地项目第一次部署上线，给朋友或客户试用
3. 推送前想核对「改了什么、推了什么」，怕线上和本地不一致
4. 线上页面没有样式，或收到提示说报错页面能看到内部信息
5. 想让「不存在的对象」返回「找不到」而不是服务器错误

### 语言信号

- 「本地好好的，线上怎么就不一样了？」
- 「怎么把项目部署上线？」「线上页面没有样式」
- 「提交推送之前我要检查什么？」
- 英文: "deploy django to heroku", "DEBUG False ALLOWED_HOSTS", "Procfile gunicorn"

### 与相邻能力的区分

- 与 `django-project-basics` / `django-user-accounts` 的区别: 它们把功能与保护面做完；本卡接手「外观 + 上线 + 加固」，不改任何取数逻辑。
- 与 `git-version-control` 的区别: 本卡只把 Git 的「提交 → 状态干净 → 推送」当作部署流程的一环；版本控制本身的完整口径（提交粒度、回退、检出）见那一条。

## E — 可执行步骤 (Execution)

1. **定依赖与运行时声明**
   - 完成标准: 在活动虚拟环境里逐个安装部署所需的包（逐个装才能定位装不上的那一个）；冻结生成的清单里每个包都带版本号，并手工补上平台管理的数据库驱动；运行时声明单行、格式为小写 python + 连字符 + 三段版本号
   - 输出契约: 三份文件（依赖清单、运行时声明、忽略清单） + 一句「本地与线上将使用同一套包版本」的确认

2. **改造设置与接线**
   - 完成标准: 设置文件末尾的条件块只包住「线上才生效」的配置（数据库、代理头、允许的主机、静态资产）；启动声明无扩展名、单行、以 `web:` 开头；应用对象已由服务静态文件的包装器接管；静态文件目录里有占位文件
   - 判停条件: 不确定某个配置该不该进条件块时，按「本地开发是否也需要它」判定；需要就留在公共区

3. **在本地按启动声明预演一遍**
   - 完成标准: 用本地预演命令（书中为 `heroku local` 一类工具，属 2016 年快照）按声明文件启动，浏览器访问指定端口能看到与开发服务器一致的主页；平台不支持本地预演时（如 Windows 上的 gunicorn）跳过并记录原因
   - 判停条件: 起不来先回到第 1、2 步核对三份文件与条件块，再查平台现时文档

4. **走 Git 仪式并推送**
   - 完成标准: 忽略清单覆盖本地环境目录、缓存目录、本地数据库文件三类；提交后工作目录干净；推送后平台侧给出访问地址，进程状态为运行中
   - 判停条件: 状态不是「干净」就先补齐提交，未提交的修改不会随推送上线

5. **线上建库、加固与验证**
   - 完成标准: 线上执行迁移，输出中出现 `Applying ...OK`；线上另建超级用户；允许的主机只列自有域名、调试开关为关；请求一个不存在的地址只看到通用错误页；取不存在对象的页面返回「找不到」而不是服务器错误
   - 判停条件: 迁移与加固都验证通过后，才把地址交给试用者；本地数据不复制到线上

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 功能还没跑通就急着做样式——顺序反了：先让程序正确运行，样式与部署都在其后。
- 不打算用托管平台时——本卡的命令序列与免费层规则绑定特定平台；换平台要按目标平台重写工作单。
- 没有版本控制基础、也不打算用 Git 时——推送式部署的每一步都建立在「提交 → 推送」之上，先补 `git-version-control`。

### 作者在书中警告的失败模式

- **ce189（带着调试开关上线）**: 调试开关随代码上线，任何触发错误的人都能看到完整堆栈、配置片段与源码路径，等于把内部结构公开；页面能正常打开，因此极易被忽略。
- **ce183（空目录不会被推送）**: 新建的空静态目录不进仓库，线上静态文件收集失败、样式全丢，而本地一切正常——必须放占位文件。
- **ce185（不忽略本地数据库）**: 把本地数据库文件纳入版本控制并推送，会在部署时用本地测试库覆盖线上库，线上用户数据整批丢失，且推送过程没有任何警告。
- **ce187（部署流程会不断变化）**: 按书中的界面与命令操作时步骤对不上（按钮位置、命令参数、依赖版本都可能变）——这是外部平台的时间属性，不是操作者的问题，遇到就对平台现时文档。

### 作者的盲点 / 时代局限

- **2016 年快照，按现环境替换**: 平台工具链、命令行工具、免费层规则（如活动时长配额与闲置休眠）与示例包版本（Django 1.8.4 等）都须按现时环境重核；书中自己也声明部署流程会不断变化。
- 密钥处理只到「对于一个练习项目而言，这足够了」（作者自认边界）——生产站点需要更细致的处理，本卡不提供。
- Windows 上有两处缺口：部分包可能装不上、本地服务器组件不能运行，第 3 步的本地预演直接跳过（ce184）——「本地先跑通再上线」的主线在 Windows 上有一段是空的。
- 样式改造的验收在书中全靠截图，而图 20-1～20-3 的内容在文本转档中整体丢失（只剩图注）；行内加圈标记丢失还造成「在 处」式的悬空指代，抄写时以正文脉络为准。

### 容易混淆的邻近方法论

- `django-project-basics`、`django-user-accounts`: 两条前置——本卡的部署对象就是它们交付的项目；功能与归属保护没跑通，加固无从谈起。
- `git-version-control`: 本卡只用到「提交-推送」环节；撤销、检出、分支与回退分级见那一条。
