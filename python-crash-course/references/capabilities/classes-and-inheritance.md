# 类与继承（第9章）

## R — 原文 (Reading)

> 对于父类的方法，只要它不符合子类模拟的实物的行为，都可对其进行重写。为此，可在子类中定义一个这样的方法，即它与要重写的父类方法同名。这样，Python将不会考虑这个父类方法，而只关注你在子类中定义的相应方法。
>
> — 第9章 9.3.4 重写父类的方法（L11190-L11190）

## I — 方法论骨架 (Interpretation)

类＝「有关如何创建实例的说明」，按它创建对象叫实例化。约定先行：**类名用驼峰命名法**（每个单词首字母大写、不用下划线），实例名与模块名用小写加下划线。`__init__()` 是特殊方法，每次创建实例时自动运行；它的形参 `self` 由 Python 自动传入、且必须排在所有形参之前；**只有带 `self.` 前缀的赋值才把值绑定到实例、成为属性**，否则只是方法内的局部变量。

硬规则一条：**类中的每个属性都必须有初始值**，哪怕这个值是 0 或空字符串；需要外部指定的做成 `__init__` 的形参，总有合理默认的直接写死。修改属性值有三条通道——直接通过实例改、通过方法设置、通过方法递增；带规则（如不许把里程表往回调）的改法收进方法，但作者自己划了底线：能运行程序的人仍可直接访问属性，「基本检查」之外还需特别注意细节。

继承解决复用：定义子类时在括号内指定父类，父类必须包含在当前文件中且位于子类前面（跨模块时要先导入）；子类 `__init__` 的第一行用 `super().__init__(…)` 初始化父类部分，之后再添加子类特有属性与方法。**重写必须与父类方法同名**——同名才算覆盖，不同名只是新增方法，父类版本照旧生效。归属判据：任何同类实例都有的属性/方法放父类，只有子类特有的才放子类。

类越写越长时不要硬撑：把其中一块提取成独立的小类，再把这个类的实例用作属性（`self.battery = Battery()`）——**组合优于把细节堆进一个类**。组织上先在一个文件里跑通、确定正确后再拆进模块；导入类优先「整模块 + 句点」或只导入用到的类，不用星号；收尾按类编码风格四条核对。

## A1 — 书中的应用 (Past Application)

### 案例 1: Dog 类——从定义到创建多个实例
- **类型**: 原书例题（可运行示范）（第9章 9.1）
- **问题**: 从零定义第一个类，弄清 __init__、self 与属性的关系
- **方法论的使用**: class Dog(): 加文档字符串；def __init__(self, name, age) 中用 self.name = name、self.age = age 存属性；另写 sit()/roll_over() 两个只需形参 self 的方法；创建 my_dog = Dog('willie', 6)，用句点访问属性、调用方法
- **结论**: 实例化时 Python 自动调用 __init__ 并返回实例，self 自动传递；每个实例有自己一组属性，可按需创建任意数量实例
- **结果**: 输出 My dog's name is Willie. / My dog is 6 years old. / Willie is now sitting. / Willie rolled over!；第二个实例 Lucy 同理得到独立的属性

### 案例 2: Car 里程表——修改属性值的三种方式
- **类型**: 原书例题（可运行示范）（第9章 9.2）
- **问题**: 里程表读数怎样改、要不要加校验
- **方法论的使用**: ① 直接改 my_new_car.odometer_reading = 23；② 通过 update_odometer(23) 修改（方法内做「新读数不小于原读数」的基本检查，回拨时打印警告）；③ 通过 increment_odometer(100) 递增
- **结论**: 有替你更新属性的方法就无需直接访问属性；但作者提醒这些检查只是「基本检查」——能访问程序的人仍可直接改属性，防不住
- **结果**: 依次输出 This car has 0 miles on it. / This car has 23 miles on it. / 回拨时 You can't roll back an odometer! / 递增后 This car has 23600 miles on it.

### 案例 3: ElectricCar——继承、重写与把实例用作属性
- **类型**: 原书例题（可运行示范）（第9章 9.3）
- **问题**: 让汽车类扩展出电动汽车：复用父类、剔除不需要的行为、收拾越来越长的清单
- **方法论的使用**: class ElectricCar(Car) 的子类 __init__ 首行 super().__init__(make, model, year)；给子类新增 self.battery_size = 70 与 describe_battery()；重写 fill_gas_tank() 输出「不需要油箱」；再把电瓶内容拆成 Battery 类，用 self.battery = Battery() 组合，经 my_tesla.battery.describe_battery() 逐级调用
- **结论**: 继承先 super 初始化父类、重写必须同名；细节越加越多时「可以将大型类拆分成多个协同工作的小类」，每个实例自动包含一个 Battery 实例
- **结果**: 输出 2016 Tesla Model S；重写版打印 This car doesn't need a gas tank!；组合版 70kWh 报约 240 英里、85kWh 报 270 英里（This car can go approximately 240 miles on a full charge.）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要把一组数据和操作它的方法绑在一起（用户、订单、棋盘棋子、飞船、书籍），让状态和动作同行
2. 写出的两个类几乎一样、属性初始化代码复制粘贴，想抽一个父类复用
3. 子类里改了方法但运行结果没变；或继承链搭好后一创建实例就报错
4. 一个类的属性和方法清单、文件越来越长，想把其中一块拆出去
5. 类写好了想放进独立文件让主程序导入，结果导入处报错或行为不对

- 与 `functions-and-modules` 的区别: 类中的方法是函数的特化——传参、返回值、文档字符串规则原样适用；本卡管的是「类/实例」这层组织单位，只在需要把状态与行为绑成一体时使用
- 与 `unit-testing` 的区别: 本卡保证类「能用」——初始值齐、继承接线正确、重写生效；为类写测试用例、在改动中守住行为属于那张卡
- 与 `pygame-project-setup` 的区别: 本卡是通用底座（定义类、继承、组合）；游戏线把类实例装进主循环、编组与设置对象，属项目专用组合

## E — 可执行步骤 (Execution)

1. **定类骨架与命名**
   - 完成标准: 类名驼峰、不用下划线；计划中的实例名小写加下划线且语义对应；类定义后紧跟一段三引号文档字符串
   - 判停条件: 若只是几个纯过程、没有要绑定保留的状态，转回函数方案

2. **写 __init__ 与初始值清单**
   - 完成标准: `__init__(self, …)` 中 self 位于所有形参之前；每个属性都在 __init__ 内有初值（哪怕 0、空串、True）；需要外部指定的做成形参、否则写死默认值；赋值一律带 `self.` 前缀
   - 输入契约: 一张「属性名 → 初值来源（形参 / 写死）」清单

3. **加方法与修改通道**
   - 完成标准: 每个方法只做一件与类主题相关的事；要改属性时优先提供 update_xxx()/increment_xxx() 方法并把校验放进方法内（如不许回拨）；在注释里写明「直接赋值仍可绕开」的边界，不宣称安全
   - 输出契约: 类外代码通过方法或只读方法访问属性

4. **复用决策：先判断继承还是组合**
   - 完成标准: 「是」关系（电动汽车是汽车）才用继承——子类括号内指定父类、父类先于子类出现（同文件）或先被导入（跨模块）；子类 __init__ 第一行 super().__init__(…)；重写方法与父类逐一核对同名，并确认输出与父类版本不同；「有」关系（车有电瓶）拆成独立小类、以实例作属性，优先组合而不是层层加深继承
   - 判停条件: 出现「细节越加越多、清单和文件越来越长」就启动拆类

5. **拆模块并接好导入**
   - 完成标准: 先在单文件跑通再拆（作者的工作流程）；模块只放类、带模块级文档字符串；主程序用 `import 模块` + `模块名.类名`，或 `from 模块 import 类名`；全文件无星号导入；跨模块继承时子类所在模块顶部显式 import 父类
   - 判停条件: 创建子类实例才报错时，先查父类是否已导入

6. **按类编码风格收尾自检**
   - 完成标准: 对照四条约定——驼峰类名、下划线实例名与模块名；每个类都有文档字符串；类内用一空行分隔方法、模块内用两空行分隔类；import 先标准库、加一空行、再写自己编写的模块

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 只有几个纯计算过程、彼此不共享状态：用函数即可，包成类是多余的一层
- 只是当数据载体、没有行为的纯记录：先考虑字典等更轻的结构，别为封装而封装
- 属性安全要求高（需要对写入做真正控制）：原书只到「基本检查」，真正的访问控制超出其范围

### 作者在书中警告的失败模式

- ce64: self 语义——不写 `self.` 前缀的赋值只是方法内的局部变量，其他方法访问不到；self 由 Python 自动传入，手动补传或漏写形参都会让实参与形参错位
- ce62: 重写必须同名——名字不同时子类只是新增了一个方法，父类方法照旧被继承并生效，想禁止的行为没有被禁止
- ce66: 忘记导入父类——子类所在模块没有 import 父类时，定义时看似正常，直到创建子类实例时才引发错误
- ce60/ce59: 方法里的「基本检查」防不住直接访问属性（能运行程序的人可以把值改成任何值）；而任何属性都必须先在 __init__ 里赋初值，没有初值的属性不是「空」，是根本不存在

### 作者的盲点 / 时代局限

- 2016 年快照，按现环境替换：书中按 Python 3.5 写作并与 Python 2.7 写法并列——`class Car(object)`、`super(ElectricCar, self)` 这类旧写法现属历史资料，只用 3.x 的无参 super()；OrderedDict（9.5）在现环境已非必需，普通字典即保留插入顺序，书中未提这一点
- 原书未提供真正的封装与访问控制（只到「基本检查」），也未讨论多重继承、抽象类等进阶内容
- 「现实世界的建模方法并没有对错之分」是作者的过程观；「该放父类还是子类」只给了一条归属判据（任何汽车都有的放父类），复杂取舍仍靠实践
- 转档提醒：本卡依据的电子文本中，「注意」条被页内孤立数字切断、代码缩进被压平、行内标记 ❶❷❸ 丢失造成悬空指代——回引示例代码请以原书排版为准

### 容易混淆的邻近方法论

- `functions-and-modules`: 方法即函数——传参方式、返回值、文档字符串等规则原样适用；本卡只处理「类/实例」这层组织单位，两者不要互相抢场
- `unit-testing`: 类是需要被测试的典型对象（用 setUp() 一次建实例、多方法复用）；本卡先把类接线做对，测试在其上展开
