# Web API 取数：GitHub 与 Hacker News（第17章）

## R — 原文 (Reading)

> Web API是网站的一部分，用于与使用非常具体的URL请求特定信息的程序交互。这种请求称为API调用。请求的数据将以易于处理的格式（如JSON或CSV）返回。依赖于外部数据源的大多数应用程序都依赖于API调用，如集成社交媒体网站的应用程序。
>
> — 第17章 使用Web API（L23330-L23330）

## I — 方法论骨架 (Interpretation)

API 调用 = 程序用「非常具体的 URL」向网站请求特定信息，数据以易于处理的格式（JSON/CSV）返回。这条能力的固定流程是**三步核验**：

**① 拼 URL**：URL 由三段构成——API 端点（如 `https://api.github.com/`）+ 资源路径（如 `search/repositories`）+ 查询参数（`?q=language:python&sort=stars`）；每一段都要能念出含义，参数决定你拿到什么数据。

**② 核验响应**：`requests.get(url)` 后先打印 `status_code`（200 表示成功），再 `r.json()` 转成 Python 字典；**先打印概述再取字段**——总数（total_count）、本次返回条数、单条记录的键数与键列表，确认「收到了期望的信息」后才研究具体字段。复杂调用还要检查完整性标志（incomplete_results）。

**③ 提取与边界处理**：可选字段可能缺键——用 `dict.get(key, 默认值)` 兜底（无评论的文章没有 'descendants' 键）；相近字段先确认语义（descendants 是整棵回复树的总数、kids 只是直接回复）；要排序就用 `sorted(..., key=itemgetter('comments'), reverse=True)`。

三条固定边界意识：**数字是运行时刻快照**——同一接口在书中三处就有三个总数，不要拿任何固定数字当验收；**本次返回条数 ≠ 命中总数**——单次返回有默认上限（示例为 30 条），翻页等做法原书未给；**请求要配额**——速率限制（limit/remaining/reset 三值）决定你能跑多快，用完只能等重置。作者断言：使用任何 API 来访问和分析信息时，流程都与此类似。

## A1 — 书中的应用 (Past Application)

### 案例 1: python_repos.py——GitHub 搜索的 URL 构成与响应核验
- **类型**: 原书例题（可运行示范）（第17章 17.1.2–17.1.4）
- **问题**: 用程序找出 GitHub 上按星级排序的 Python 仓库
- **方法论的使用**: 拼 URL——`https://api.github.com/search/repositories?q=language:python&sort=stars`（端点 + search/repositories + 查询实参：q 表示查询、language:python 限定语言、&sort=stars 按星级排序）；`r = requests.get(url)`；打印 status_code 核验；`response_dict = r.json()` 后打印字典的键
- **结论**: 状态码 200 表示请求成功；响应字典有三个键（items / total_count / incomplete_results）——简单调用可忽略完整性标志、复杂调用必须检查
- **结果**: 输出 Status code: 200 与三个键的字典（'items'、'total_count'、'incomplete_results'）；数值为运行时刻快照

### 案例 2: 处理响应字典——先输出概述，再研究字段
- **类型**: 原书例题（可运行示范）（第17章 17.1.5–17.1.6）
- **问题**: 从响应里取出项目名称、星数等信息；单条记录字段很多，不知道能提取什么
- **方法论的使用**: 先打印概述——`response_dict['total_count']`、`len(repo_dicts)`、单条记录的键数，并用 `sorted(repo_dict.keys())` 打出全部 68 个键；再打印第一个仓库的关键值（Name / Owner / Stars / URL / 时间 / 描述）；最后循环处理每条记录。owner 是嵌套字典，要逐层取
- **结论**: 「确认收到了期望的信息，进而可以开始研究感兴趣的信息」——先核对再取字段；不知道 API 返回什么时，要么读文档、要么用代码打印键
- **结果**: 输出 Total repositories: 713062、返回 30 条、68 个键；首个仓库 httpie（16101 星）

### 案例 3: hn_submissions.py——批量取数、缺键兜底与排序
- **类型**: 原书例题（可运行示范）（第17章 17.3）
- **问题**: 找出 Hacker News 上讨论最激烈的文章：先拿到最热文章的 ID 列表，再变出可排序的标题/评论数清单
- **方法论的使用**: 取 topstories 列表（约 500 个 ID 的 JSON），对前 30 个 ID 逐篇请求详情；每篇构造字典时用 `response_dict.get('descendants', 0)` 兜底无评论文章；最后 `sorted(submission_dicts, key=itemgetter('comments'), reverse=True)` 按评论数降序
- **结论**: 缺键是常态（可选字段只在有值时出现），dict.get 把它变成默认值场景；相近字段语义要分清（descendants 含全部次级回复，kids 只是直接回复）
- **结果**: 打印各篇文章的标题、讨论链接与评论数（Comments: 231 / 142 / 141 / 75 / 14 …），评论最多的在最前

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 想让脚本自动从网站/服务取数据（仓库榜单、新闻热帖、天气、价格），不想手工复制
2. 照着教程调 API，出来的数字与教程对不上，怀疑自己写错了
3. 程序跑一会儿开始报错或返回空，但代码没改（配额/速率限制）
4. 要把取回的数据做成图表交付（榜单条形图、地图）
5. 拿到一份不熟悉的 API 响应，不知道结构、不知道从哪开始摸

## E — 可执行步骤 (Execution)

1. **拼 URL 并发出请求**
   - 完成标准: URL 由「API 端点 + 资源路径 + 查询参数（?q=…&sort=…）」三段构成，每段含义能用一句话念出；明确是否需要密钥、预期返回什么
   - 输入契约: 端点、资源路径、查询参数（语言、排序、条数等）

2. **核验响应再解析**
   - 完成标准: 打印 status_code 并确认 200；r.json() 后先打印概述（总数、本次返回条数、单条记录的键数与键列表）再进入字段提取；复杂调用读取完整性标志（incomplete_results）
   - 判停条件: 非 200、条数为 0 或明显异常时，先查配额（第 4 步）再继续，不要反复重跑

3. **提取字段并处理缺键与近义字段**
   - 完成标准: 可选字段一律 dict.get(key, 默认值) 兜底（如无评论文章计 0）；使用前确认字段语义（descendants 与 kids 的区别），并在产出物里写明排序/统计口径
   - 输出契约: 结构化条目列表（每条含所需的标题/数值/链接等字段）

4. **控制请求节奏与批量模式**
   - 完成标准: 能报出本次调用的配额状态（limit / remaining / reset）；「列表→逐条详情」的循环明确条数与失败处理，避免短时间内反复重跑耗尽配额
   - 判停条件: 配额耗尽只能等重置，等待期间不要重试轰炸

5. **交付并附边界声明**
   - 完成标准: 产出物（数据或图表）附两句边界——「本次返回条数不等于命中总数（单次默认上限）」与「数值是请求时刻快照，重跑会变」；翻页、失败重试、密钥注册等书中未给的做法如实标注未给

## B — 边界 (Boundary) ★

### 不要在以下情况使用

- 离线环境、或目标服务要求注册/密钥而你没有准备时——先解决凭据与网络，再谈调用
- 只取一次、量又小、手工导出更省事时——自动化的成本不划算
- 想拿某次运行的数字当固定基线做验收时——实时接口的输出天然不能当断言

### 作者在书中警告的失败模式

- ce152: 书中同一个 API 的总数在三处不同（713062 / 713065 / 713067）——读者拿本地运行结果与书核对必然「对不上」，误以为代码写错
- ce159: 字典键可能不存在（无评论的文章没有 'descendants'）——直接下标访问抛 KeyError，且只发生在少数条目上
- ce154: 结果条数被默认分页截断（30 条是单次上限）——当成「全部最受欢迎仓库」会静默漏掉后面的数据
- ce157: 速率限制用完只能干等——反复调试很快耗尽每分钟 10 次的搜索配额，之后的请求只返回「已达极限」，表现为数据为空而代码没毛病

### 作者的盲点 / 时代局限

- 2016 年快照：GitHub 的配额口径（搜索每分钟 10 次）、Hacker News 的接口与 requests/Pygal 版本均为当时状态；接口与配额规则会实时漂移，须以当前文档为准、按现环境替换
- 书中把实时数据当固定输出呈现（同一总数三处互不相同），且未给翻页、失败重试与 API 密钥注册的具体做法——这些缺口只能自行补齐
- 示例程序没有节流/重试机制；「列表 + 循环内逐条详情」的请求模式在失败时只体现在打印的状态码里
- 转档缺陷：图17-1~17-4 的内容丢失、只剩图注，图表外观与工具提示效果无法按书核对

### 容易混淆的邻近方法论

- `data-parsing-and-cleaning`: 面对本地文件与已下载数据；本 skill 面对在线响应，多了「状态码 / 完整性标志 / 配额」三道核验
- `data-visualization`: 呈现环节归它；本 skill 的终点是干净、已核验的数据结构
